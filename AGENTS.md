# Правила работы с репозиторием CS Registry

Документ для любой LLM-ассистента, которая работает с этим кодом. Читай его целиком
перед первой правкой. Здесь только то, что нельзя вывести из кода.

## 1. Что это за система

Реестр компьютеризированных систем фармпроизводства. Регуляторный контекст: GxP,
ALCOA+, 21 CFR Part 11, валидация по GAMP 5 категории 5 (заказная разработка).

Из этого следует главное: **журнал аудита — не логи, а регуляторная запись.** Его нельзя
переписать, обойти или «почистить». Любая правка, которая позволяет изменить или удалить
событие аудита, — это дефект, даже если она удобнее.

Стек: Node 22, pnpm 10, Next.js 16 (App Router), TypeScript strict, PostgreSQL 16,
Drizzle ORM, Zod, Vitest, Playwright.

## 2. Железное правило: гейт

Перед любым мёржем в `main` обязан пройти локальный гейт:

```bash
pnpm ci:local
```

Он запускает lint, typecheck, unit-тесты, интеграционные тесты, сборку и три
браузерных сценария. **Код возврата должен быть 0.** Не «почти всё зелёное», не
«упал один нестабильный тест» — ноль.

Почему так строго: в этом проекте восемь дефектов подряд проходили зелёный гейт и
ломались на другой машине. Каждый раз причина одна — проверка писалась там, где под
рукой были нужные условия. Поэтому:

- гейт гоняется **до** отправки ветки, а не после;
- упавший тест чинится в причине, а не отключением проверки;
- `it.skip`, `.only`, закомментированный ассерт, ослабленное ожидание — это не починка.

Если тест падает только у тебя и проходит у других — ищи разницу в окружении
(версия Node, наличие Chrome, шрифты, локаль), а не переписывай ожидание под свой
результат.

## 3. Как делать мёржи

**Прямой push в `main` запрещён.** Только ветка и pull request.

Порядок:

1. Ответвись от `main`: `git switch -c <тип>/<короткое-имя>`.
   Типы: `fix/`, `feat/`, `docs/`, `chore/`.
2. Сделай работу. Один PR — одна тема.
3. Прогони `pnpm ci:local`, добейся нуля.
4. Запушь ветку, открой PR с описанием: что было не так, что изменилось, как проверено.
5. Дождись ревью человеком — владельцем системы.
6. Мёржи **только после** зелёного гейта и одобрения.

**Стратегия слияния — merge commit, не squash.** Причина в ALCOA+: принцип
«original» требует сохранять исходную запись. Squash схлопывает пять коммитов в
один и уничтожает промежуточную историю: кто, когда и почему менял каждую строку.
Для регуляторного проекта это потеря данных, а не уборка мусора. Пусть история
будет шумной — она должна быть настоящей.

Перебазирование и `force push` в общую ветку запрещены. В свою личную ветку до
открытия PR — можно, после открытия — уже нет: ревьюер смотрел одну версию, а
мёржится другая.

## 4. Версии

Версия живёт в одном месте — поле `version` в `package.json`. Документы в `docs/`
имеют свой `version` в YAML front-matter и шагают по semver вместе с системой.

- **MAJOR** — ломающее изменение смысла или схемы данных.
- **MINOR** — новое требование, новый раздел, новая возможность.
- **PATCH** — правка формулировок, исправление дефекта без изменения смысла.

Версия документа **не может обгонять** MAJOR-версию системы. Сейчас MAJOR = 0,
поэтому все документы в диапазоне 0.8.x.

Версию поднимает тот, кто меняет код или документ, в том же коммите. Отдельным
«релизным» коммитом — нельзя, забудется.

## 5. Чего делать нельзя

- Менять `audit_events`: `UPDATE`, `DELETE`, `TRUNCATE` по этой таблице. Триггер
  поднимет исключение — это защита, а не помеха.
- Ослаблять права прикладной роли БД: у неё нет `UPDATE`/`DELETE` на журнал
  намеренно.
- Возвращать в интерфейс технические коды и английские подписи. Весь UI — русский,
  человеческим языком. `REASON_REQUIRED` — это код API для машины, пользователь
  видит «Для этого изменения нужна причина».
- Класть секреты в репозиторий. `.env` в `.gitignore`, шаблон — `.env.example`.
- Пушить в `main` напрямую, мёржить без гейта, отключать тест ради зелёного прогона.
- Менять миграции, которые уже применены. Только новая миграция поверх.

## 6. Требование причины

Правка требует заполненного `reason`, если меняется критичное поле
(`criticality`, `is_gxp_relevant`, `validation_status`), если система уже
валидирована, а также при архивировании, восстановлении и смене роли.

Во всех остальных случаях причина необязательна, но если её передали — она
попадает в аудит. Отказ по причине пишется в журнал отдельным событием с кодом
`REASON_REQUIRED`. Это правильно: попытка обойти правило — тоже регуляторный факт.

## 7. Развёртывание

`docker-compose.yml` поднимает **только PostgreSQL**. Приложение запускается
отдельно.

```bash
# 1. База
cp .env.example .env          # заполнить пароли
docker compose up -d db

# 2. Зависимости и схема
pnpm install --frozen-lockfile
pnpm db:migrate

# 3. Сборка и запуск
pnpm build
pnpm start                    # http://127.0.0.1:43123
```

Требуется Node 22 и pnpm 10.33.4. Для браузерных тестов — Chrome либо
`pnpm exec playwright install chromium`.

Проверка живости: `curl http://127.0.0.1:43123/api/health` — версия должна совпасть
с `package.json`.

## 8. Проверка целостности журнала

```bash
pnpm audit:verify
```

Печатает «Цепочка цела» и код 0, либо номер записи с разрывом и код 1. Гонять после
восстановления из резервной копии и периодически в эксплуатации. Разрыв цепочки —
инцидент, а не «шум в логах»: останови приём изменений и разбирайся.

## 9. Где что лежит

- `docs/INITIAL-CONTEXT.md` — исходные решения и допущения проекта.
- `docs/specification/urs.md` — пользовательские требования, URS-NNN.
- `docs/specification/functional-specification.md` — функциональная спецификация,
  экраны SCR-*, контракт API, коды ошибок.
- `docs/architecture/` — контекст, C4, ER-модель.
- `docs/operations/` — проверка цепочки аудита, резервное копирование.
- `scripts/ci-local.sh` — гейт.

Требование с номером URS-NNN — это контракт. Меняешь поведение, которое оно
описывает, — обнови требование и документ в том же PR, иначе код и спецификация
разъедутся, и следующая LLM будет чинить одно, ломая другое.

## 10. Порядок, если что-то сломалось

1. Прочитай сообщение об ошибке до конца, а не первую строку.
2. Воспроизведи на чистой базе: `pnpm db:migrate` на пустой `cs_registry_test`.
3. Найди причину. «Попробую вот так, вдруг поможет» — не метод.
4. Починив, добавь тест, который падал бы без починки. Проверь это обратным ходом:
   временно верни дефект и убедись, что тест краснеет.
5. Прогони гейт.

Пятый пункт не пропускается никогда.

# Реестр компьютеризированных систем — первичный контекст

Документ фиксирует исходные решения для нового проекта: что строим, на каких
допущениях, какая архитектура, модель данных, ролевая модель и требования к
аудиту. Всё, что помечено «допущение», требует подтверждения владельцем.

## 1. Назначение

Единый источник правды о компьютеризированных системах организации: какие
системы существуют, что они делают, кто за них отвечает, какие данные в них
хранятся, насколько они критичны, валидированы ли они, и полная неизменяемая
история изменений каждой записи.

Проблема, которую решаем: реестр систем обычно живёт в разрозненных Excel-файлах
и почте. Никто не знает актуальную версию, кто владелец, когда истекает
периодическая переоценка, и кто изменил запись. При проверке (внутренний аудит,
инспекция) восстановить историю невозможно.

## 2. Допущения

- **A-1.** **Подтверждено заказчиком:** контекст GxP. Данные реестра должны
  соответствовать ALCOA+. К разработке применяется 21 CFR Part 11, сам реестр
  подлежит валидации компьютеризированной системы (КС) по GAMP 5.
- **A-1.1.** **Подтверждено заказчиком:** электронная подпись записей в
  демонстрационной версии не требуется. Схема и код оставляют под неё место, но
  реализация ЭП — вне текущего объёма. Обоснование отсутствия ЭП фиксируется в
  валидационном отчёте как ограничение области.
- **A-1.2.** **Подтверждено заказчиком:** результаты демонстрируются в
  интерфейсе и через выгрузки XLSX и PDF. Выгрузки — часть валидируемого объёма,
  а не вспомогательная функция.
- **A-2.** Один тенант, одна организация, несколько площадок. Мультитенантность
  не входит в MVP, но схема БД не должна её исключать.
- **A-3.** Язык интерфейса и данных — русский. Поиск обязан корректно работать с
  русской морфологией и латиницей в названиях вендоров.
- **A-4.** Развёртывание на одном VPS в РФ, Docker Compose, TLS через Caddy.
- **A-5.** Объём: до 5 000 систем, до 50 одновременных пользователей. Этого
  достаточно для PostgreSQL без выделенного поискового движка.

## 3. Границы MVP

Входит:

1. Каталог систем: список, карточка, создание, редактирование, архивирование.
2. Живой поиск (ввод → результаты без перезагрузки) и фильтры по типу,
   критичности, статусу жизненного цикла, владельцу процесса, площадке.
3. Ролевая модель с серверной проверкой прав на каждом действии.
4. Аудит-трейл: неизменяемая запись обо всех изменениях, просмотр и фильтрация,
   история изменений каждого объекта в его карточке (выборка из того же журнала).
5. Аутентификация административных пользователей, персональные учётки.
6. Экспорт реестра в XLSX и PDF. Выгрузка — контролируемое действие: пишется в
   аудит с параметрами фильтра, составом колонок, актором и числом записей.
   В PDF — идентификатор отчёта, время формирования, фильтры и актор.
7. Валидационный комплект документации КС: URS, план валидации, оценка рисков,
   IQ/OQ/PQ, матрица трассировки требований, отчёт о валидации, процедуры
   эксплуатации. Документы — часть поставки, а не «потом».
8. Резервное копирование в объёме первого релиза (заказчик подтвердил, что
   бэкапы должны быть предусмотрены): скрипт/задание ежедневного логического
   дампа, шифрование до отправки, документированная процедура восстановления,
   проверенная минимум один раз до демонстрации. Это граница релиза, а не
   сужение URS-070/URS-071: те требования относятся к системе целиком.

Не входит в MVP (P1 и позже):

- электронная подпись записей и workflow согласования изменений (в схеме и коде
  предусмотрены точки расширения, реализация — P1, отдельным изменением с
  переоценкой валидации);
- импорт данных из внешних систем, в том числе существующего Excel-реестра
  (подтверждено заказчиком: в MVP не входит);
- вложения и валидационная документация;
- граф интерфейсов между системами;
- интеграции с ITSM/CMDB, импорт из Active Directory;
- уведомления о приближении периодической переоценки;
- мультитенантность, публичный API для внешних потребителей.

Вне кода приложения (эксплуатация и ввод в эксплуатацию, не функция
продукта и не пункт «P1 позже»): провижининг S3-совместимого бакета,
управление ключами шифрования, политики жизненного цикла хранения.
Подтверждено заказчиком: бакет — этап ввода в эксплуатацию, а не код
приложения.

## 4. Архитектура

Модульный монолит, один деплой, один процесс. Причины: один потребитель
интерфейса, малый объём данных, отсутствие требований к независимому
масштабированию модулей. Разделение на сервисы здесь добавило бы сетевые сбои и
распределённые транзакции без выгоды — а аудит обязан быть транзакционным.

```
Браузер
  │ HTTPS
  ▼
Caddy (TLS, security headers, rate limit)
  │
  ▼
Next.js приложение (App Router, TypeScript, SSR, admin UI)
  ├── src/server/modules/auth      сессии, пароли, RBAC
  ├── src/server/modules/systems   реестр: CRUD, поиск, фильтры
  ├── src/server/modules/audit     запись и чтение аудит-трейла
  └── src/server/modules/users     учётные записи и роли
  │
  ▼
PostgreSQL (pg_trgm, unaccent, audit_events append-only)
```

Стек:

- **Next.js (App Router) + TypeScript strict.** SSR для списка, Server Actions и
  Route Handlers для мутаций и живого поиска.
- **PostgreSQL 16+.** `pg_trgm` и `unaccent` для поиска, `citext` не используем —
  нормализуем на входе.
- **Drizzle ORM + Drizzle Kit.** Схема в TypeScript, миграции как SQL-файлы,
  обратимость там, где это безопасно.
- **Auth.js (NextAuth) Credentials + Argon2id.** Сессия в httpOnly cookie,
  SameSite=Lax, ротация при смене пароля. MFA TOTP — P1, но поле в схеме есть.
- **Zod** на всех границах: вход API, парсинг env, ответы.
- **pino** для структурированных логов с correlation ID.
- **Vitest** (unit), **Testcontainers + PostgreSQL** (интеграционные, включая
  проверку неизменяемости аудита), **Playwright** (e2e критического пути).
- **GitHub Actions**: lint, typecheck, test, build, проверка миграций.
- **Docker Compose**: `web`, `db`, `caddy`. Образы собираются в CI с неизменяемым
  тегом по SHA.

Почему не NestJS: второй рантайм и второй слой маршрутизации без второго
потребителя. Модульные границы обеспечиваются структурой каталогов и правилом
«домен не импортирует HTTP», а не фреймворком. Если позже появится внешний API
или мобильный клиент — NestJS добавляется как отдельный сервис, и это осознанное
решение, а не текущая перестраховка.

GAMP 5 Second Edition, §6.1.2 требует определить и довести до сведения роли и
ответственность владельца процесса (Process Owner), владельца системы (System
Owner) и владельца данных (Data Owner) — вместе с подразделением качества,
экспертами предметной области, поставщиками и конечными пользователями — и
указать, кто что одобряет и что означает это одобрение. GAMP 5 не предписывает
конкретное поле в реестре: он требует определённые и доведённые роли. Обязательные
`process_owner_id` и `system_owner_id` (и необязательный `quality_owner_id`) —
способ этого проекта обеспечить определённость ролей в учёте КС. Безымянный
`owner_id` и замена `technical_owner_id` сняты, чтобы не смешивать Process Owner
и System Owner.

Индексы: GIN `pg_trgm` по `name`, `vendor`, `code`; btree по
`system_type`, `criticality`, `lifecycle_status`, `process_owner_id`, `next_review_at`.

## 6. Ролевая модель

Четыре роли, одна роль на пользователя. Права проверяются на сервере в каждом
защищённом действии, никогда только в интерфейсе. Принцип: запрещено по
умолчанию.

| Действие | admin | editor | viewer | auditor |
|---|---|---|---|---|
| Просмотр реестра | да | да | да | да |
| Создание системы | да | да | нет | нет |
| Редактирование системы | да | да | нет | нет |
| Архивирование | да | да | нет | нет |
| Изменение статуса валидации | да | нет | нет | нет |
| Просмотр аудит-трейла | да | нет | нет | да |
| Экспорт CSV | да | да | да | да |
| Управление пользователями и ролями | да | нет | нет | нет |

Роли:

- **admin** — управляет пользователями и ролями, подтверждает валидационный
  статус. Не может изменять или удалять аудит.
- **editor** — ведёт записи реестра (создание, правка, архивирование).
- **viewer** — читает реестр и экспортирует срез, изменять ничего не может.
- **auditor** — читает всё, включая аудит-трейл; не пишет ничего. Роль
  существует ради проверок и не должна совмещаться с admin у одного человека
  без письменного обоснования.

Правила: нет публичной регистрации; учётку создаёт admin; смена роли и
деактивация пишутся в аудит; последнего активного admin удалить нельзя.

## 7. Требования к аудиту (ALCOA+)

Каждое событие обязано быть:

- **Attributable** — actor_id + снимок логина и роли; системные события
  помечены явно.
- **Legible** — `changed_fields` и `before`/`after` читаемы человеком, не дамп
  памяти.
- **Contemporaneous** — время берётся из БД в момент транзакции, не из клиента.
- **Original** — первая запись не перезаписывается; исправление — новое событие.
- **Accurate** — запись и изменение данных в одной транзакции; откат изменения
  откатывает и аудит.
- **Complete** — фиксируются и неуспешные попытки: неверный пароль, отказ в
  доступе, неудачная валидация.
- **Consistent** — единый формат события для всех модулей, единый сериализатор.
- **Enduring** — отдельный tablespace/регулярный дамп, retention настраивается,
  по умолчанию бессрочно.
- **Available** — просмотр с фильтрами по дате, актору, объекту, действию;
  P95 выборки за месяц < 1 с.

Техническая защита от подмены:

1. Прикладная роль БД не имеет `UPDATE` и `DELETE` на `audit_events`.
2. Триггер `BEFORE UPDATE OR DELETE` поднимает исключение — защита работает даже
   при ошибке в правах.
3. Хеш-цепочка: каждая запись хранит `prev_hash` и собственный `hash`. Разрыв
   цепочки обнаруживается проверочным заданием.
4. Ежедневное задание пишет контрольную точку (последний `id` и `hash`) во
   внешнее хранилище — вне доступа прикладной роли.
5. Чтение журнала аудита само аудируется.

## 8. Поиск и фильтры

- `GET /api/v1/systems?q=&type=&criticality=&status=&process_owner=&site=&page=`
- Живой поиск: debounce 250 мс на клиенте, отмена предыдущего запроса
  (`AbortController`), минимальная длина запроса 2 символа.
- SQL: `unaccent(lower(...))` + `%` по `pg_trgm` для подстроки, приоритет —
  совпадение по началу `code` и `name`.
- Пустой результат — явное состояние «ничего не найдено» с предложением сбросить
  фильтры, а не пустая страница.
- Фильтры комбинируются по И, состояние фильтров живёт в URL (шарится ссылкой).
- Целевые метрики: P95 ответа поиска < 200 мс на 5 000 записей.

## 9. Нефункциональные требования

- Доступность 99,5% в месяц.
- TLS обязателен, HSTS после проверки домена, security headers через Caddy.
- Пароли — Argon2id, минимум 12 символов, блокировка после 5 неудач за 15 минут.
- Rate limit на вход и на поиск.
- WCAG 2.2 AA, полная клавиатурная навигация, адаптив 360/768/1280.
- Структурированные логи с correlation ID; в логи не попадают пароли, токены,
  персональные данные сверх необходимого.
- Резервные копии: ежедневный зашифрованный дамп вне VPS, 7 дневных / 4
  недельных / 6 месячных, проверка восстановления ежемесячно.
- RPO 24 ч, RTO 4 ч.


## 9a. 21 CFR Part 11 — что это значит для кода

Part 11 применяется к разработке, даже если ЭП в демо нет. Раздел 11.10 требует
от системы свойств, которые проверяются при валидации. Ниже — соответствие и
где именно оно живёт в реализации.

| Требование 11.10 | Как закрываем |
|---|---|
| (a) Валидация системы | Комплект документов КС, раздел 13 |
| (b) Возможность создавать точные и полные копии данных в читаемом виде | Выгрузки XLSX и PDF, раздел 14 |
| (c) Защита записей от изменения и удаления в течение срока хранения | Append-only аудит, права БД, триггер, хеш-цепочка; ежедневный шифрованный дамп, ротация 7 дневных / 4 недельных / 6 месячных, ежемесячная проверка восстановления |
| (d) Ограничение доступа по полномочиям | RBAC, серверная проверка, запрет по умолчанию |
| (e) Аудит-трейл с датой, временем, пользователем, типом действия | `audit_events`, время из БД в UTC |
| (f) Проверка последовательности этапов при необходимости | Не применимо: workflow без обязательных этапов, кроме смены статуса валидации (только admin, с обязательной причиной) |
| (g) Проверка полномочий и валидности учётных данных | Сессии, Argon2id, блокировка после 5 неудач, деактивация |
| (h) Проверка актуальности устройства и учётных данных | Сессия истекает, при деактивации пользователя все сессии отзываются |
| (i) Проверка подлинности источника ввода при необходимости | Не применимо: единственный источник — аутентифицированный пользователь через интерфейс |
| (j) Обучение персонала | Вне системы, фиксируется в валидационных документах |
| (k) Письменные политики подотчётности | Вне системы |
| (e)(1)–(e)(5) | Полный аудит-трейл: актор, время, действие, до/после, причина, request ID |

Отдельно: **11.200 ЭП не требуется** — подтверждено заказчиком. Но если в
будущем появится, потребуются два компонента (идентификация и подпись),
электронная подпись, привязанная к записи, и невозможность отделить подпись от
записи. Схема хранит `reason` и снимок актора именно поэтому: добавить подпись
поверх существующего события будет расширением, а не переделкой.

Обязательное требование к аудиту: **причина изменения для критичных действий.**
Изменение статуса валидации, критичности, архивирование и любое изменение
системы со `validation_status = validated` требуют непустое поле `reason`.

### Что считается критичным изменением

- `systems.validation_status`, `systems.criticality`, `systems.is_gxp_relevant`;
- архивирование и восстановление из архива;
- смена роли пользователя, деактивация;
- любое редактирование системы, у которой `validation_status = validated`.

## 9b. Валидация КС (CSV по GAMP 5)

Реестр — категория 4 по GAMP 5 (настраиваемое ПО). Валидация обязана быть
пропорциональна риску, а не равномерной.

Комплект документов (папка `docs/validation/`):

| Документ | Назначение | Владелец |
|---|---|---|
| `validation-plan.md` | Стратегия, объём, роли, критерии приёмки, категория GAMP | QA |
| `urs.md` | Пользовательские требования, каждый пункт прослеживается вниз | Бизнес |
| `risk-assessment.md` | Оценка рисков по функциям, влияние на данные и качество | QA + архитектор |
| `dq.md` | Квалификация проектирования: соответствие требований архитектуре | Архитектор |
| `iq.md` | Квалификация монтажа: окружение, версии, конфигурация, права БД | Валидация |
| `oq.md` | Квалификация функционирования: проверка функций против URS | Валидация |
| `pq.md` | Квалификация эксплуатации: сценарии на реальных данных | Бизнес + QA |
| `traceability-matrix.md` | URS → риск → тест → результат | Валидация |
| `validation-report.md` | Итоговый отчёт: отклонения, ограничения, решение о приёмке | QA |
| `sop/` | Процедуры: ведение реестра, изменение, периодическая переоценка | Бизнес |

Жёсткие правила:

1. **Ни одно требование URS без теста и результата.** Матрица трассировки
   генерируется из тех же данных, что и тесты, иначе она врёт. Это же правило
   зафиксировано в CI: тест с идентификатором требования, не найденным в URS,
   валит сборку.
2. **Валидация не бывает «потом».** Тесты пишутся вместе с функциональностью;
   IQ/OQ-процедуры готовятся до релиза, а не после.
3. **Изменение после валидации проходит переоценку.** Любой релиз после
   приёмки — через оценку влияния на валидированное состояние и, при
   необходимости, частичную ревалидацию.
4. **Версия системы фиксируется.** Каждая валидированная версия получает
   неизменяемый тег и попадает в `validation-report.md` с SHA коммита.
5. **Демонстрационная версия не объявляется валидированной.** Пока отчёт не
   подписан человеком, система в статусе «готово к демонстрации», не «валидировано».

## 9c. Выгрузки XLSX и PDF

Выгрузка — не удобство, а средство «точных и полных копий» по 11.10(b).

XLSX:

- лист «Реестр» — текущий срез с применёнными фильтрами;
- лист «Параметры выгрузки» — кто, когда, какие фильтры, число записей, версия
  приложения (SHA), имя файла;
- лист «Справочники» — расшифровка enum-значений, чтобы файл читался без системы;
- заморозка шапки, автофильтр, числовые форматы дат ISO 8601;
- `code` системы — первая колонка, идентификатор записи `id` — последняя
  скрытая служебная колонка для сверки.

PDF:

- титульная страница: заголовок, период, фильтры, актор, время формирования,
  версия приложения, идентификатор отчёта;
- таблица с повтором шапки на каждой странице, нумерация «страница X из Y»;
- на каждой странице — колонтитул с идентификатором отчёта и временем, чтобы
  отдельная страница не теряла происхождение;
- шрифт с поддержкой кириллицы, встраивается в файл.

Общее:

- формирование на сервере, потоково, без загрузки всего набора в память клиента;
- каждая выгрузка пишет событие `export` в аудит: формат, фильтры, число
  записей, request ID;
- персональные данные — только те, что в реестре есть по делу; экспорт не должен
  расширять их состав;
- имя файла: `cs-registry_<YYYY-MM-DD>_<HHMM>_<short-request-id>.<ext>`.

## 10. API (черновик)

Публичного API нет. Всё под аутентификацией.

```
POST   /api/v1/auth/login
POST   /api/v1/auth/logout
GET    /api/v1/systems
POST   /api/v1/systems
GET    /api/v1/systems/:id
GET    /api/v1/systems/:id/history
PATCH  /api/v1/systems/:id
POST   /api/v1/systems/:id/archive
POST   /api/v1/systems/:id/restore
GET    /api/v1/systems/export?format=xlsx
GET    /api/v1/systems/export?format=pdf
GET    /api/v1/audit
GET    /api/v1/users
POST   /api/v1/users
PATCH  /api/v1/users/:id
```

Каждый ответ несёт `X-Request-Id`. Ошибки — единый формат `{ code, message,
requestId }` без stack trace.

## 11. Критерии готовности MVP

1. CRUD реестра с серверной авторизацией на каждом действии.
2. Живой поиск и комбинируемые фильтры, состояние в URL.
3. Аудит пишется для каждого изменения и для неуспешных попыток; `UPDATE` и
   `DELETE` по `audit_events` физически невозможны — есть тест, который это
   доказывает.
4. Хеш-цепочка проверяется заданием (`pnpm audit:verify`), разрыв обнаруживается;
   контрольная точка (`id`, `hash`) пишется во внешний файл.
5. Восстановление из резервной копии выполнено хотя бы один раз вручную
   (процедура `docs/operations/backup-restore.md`, политика 7/4/6).
6. Playwright-сценарий: вход → создание системы → поиск → правка → причина
   изменения → просмотр аудита → история изменений в карточке
   (`e2e/critical-path.spec.ts`).
7. Выгрузки XLSX и PDF формируются на сервере, содержат параметры выгрузки и
   пишут событие `export` в аудит.
8. Требование `reason` работает: попытка изменить критичное поле без причины
   отклоняется и в аудит попадает отказ.
9. Гейт качества: lint, typecheck, unit, integration, build. Файл GitHub Actions
   готов, но репозиторий в Cursor Origin — Actions не запускается. Предполёт —
   `pnpm ci:local`. Интеграционные тесты изолированы от демо-базы
   (`TEST_DATABASE_URL`).
10. Валидационный комплект в состоянии «готов к исполнению»: URS, план,
    оценка рисков, IQ/OQ-процедуры, матрица трассировки. Подписанный отчёт — за
    человеком.
11. История изменений объекта доступна из карточки; полный перечень защищённых
    действий покрыт аудитом, это проверяется тестом.

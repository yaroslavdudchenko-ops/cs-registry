# Функциональная спецификация

Спецификация описывает поведение демонстрационной версии. Публичного каталога нет: все данные реестра доступны только после аутентификации. Единственный экран без сессии — вход; он не публикует сведения о системах. Категория GAMP 5 — **5** (заказная разработка). ЭП не требуется (решение заказчика 29.10.2026).

Идентификаторы экранов и разделов стабильны для трассировки на URS.

## 1. Маршруты и экраны

| ID | Маршрут | Экран | Роли | Сессия |
|---|---|---|---|---|
| SCR-LOGIN | `/login` | Вход | нет | не требуется; при валидной сессии редирект на список |
| SCR-LIST | `/systems` | Список систем | admin, editor, viewer, auditor | да |
| SCR-NEW | `/systems/new` | Создание системы | admin, editor | да |
| SCR-CARD | `/systems/:id` | Карточка системы | admin, editor, viewer, auditor | да |
| SCR-EDIT | `/systems/:id/edit` | Редактирование системы | admin, editor | да |
| SCR-AUDIT | `/audit` | Журнал аудита | admin, auditor | да |
| SCR-USERS | `/users` | Пользователи | admin | да |

Неаутентифицированный запрос к любому маршруту кроме `/login` перенаправляет на `/login` с `callbackUrl`. Роль без права получает экран «нет прав» (HTTP 403 для API), а не пустой список, маскирующий запрет.

Маршрутов `/register`, `/api/docs`, публичного лендинга с данными реестра нет.

## 2. Поведение экранов

Общие состояния, применимые к защищённым экранам:

| Состояние | Когда | Что видит пользователь |
|---|---|---|
| loading | запрос данных не завершён | скелетон таблицы или карточки, без пустых нулей, которые можно принять за данные |
| empty | запрос успешен, выборка нулевая | для списка без фильтров — «В реестре пока нет систем» и кнопка создания, если роль позволяет; для поиска — «Ничего не найдено» и сброс фильтров |
| error | 5xx, сеть, таймаут | сообщение «Не удалось загрузить данные», `requestId`, кнопка повтора |
| нет прав | 403 | «Недостаточно прав для этого действия»; без утечки тела запрещённого объекта сверх уже известного идентификатора |

Ошибки валидации показываются у полей. Глобальная ошибка мутации показывает `message` и `requestId` из тела `{ code, message, requestId }`. Отсутствие `process_owner_id` или `system_owner_id` при создании и сохранении — HTTP 422 `OWNERS_REQUIRED`, сущность не пишется, в аудит попадает отказ (URS-091).

Навигация критического пути (вход → список → карточка → журнал) доступна с клавиатуры. Вёрстка проверяется на ширинах 360, 768 и 1280. Это целевой уровень WCAG 2.2 AA (URS-075, Should), а не отдельный экран.

### 2.1. SCR-LOGIN — Вход

Поля: `username` (текст, нижний регистр на сервере), `password` (секрет).

Поведение:

- Отправка вызывает `POST /api/v1/auth/login`.
- Успех: Set-Cookie сессии (`sid`, HttpOnly, SameSite=Lax), `Max-Age` по роли: 1800 секунд (30 минут) для `admin`, 600 секунд (10 минут) для `editor` / `viewer` / `auditor`. Редирект на `/systems` или `callbackUrl` внутри приложения.
- Неверные учётные данные: одно и то же сообщение «Неверный логин или пароль», без уточнения, какой фактор неверен; пишется `login_failed`.
- Блокировка: сообщение о временной недоступности входа, без обхода через другой текст ошибки.
- Пустые поля: клиентская и серверная валидация, запрос не уходит с пустым паролем.

Состояния: loading на время запроса; error при 5xx; отдельного empty нет.

### 2.2. SCR-LIST — Список систем

Состав колонок: `code`, `name`, `system_type`, `criticality`, `lifecycle_status`, владелец процесса (`full_name`), `site`, `validation_status`. Код системы и короткие справочные значения (тип, критичность, статус жизненного цикла, статус валидации) отображаются одной строкой, без переноса по дефису. Наименование и площадка переносятся. Ширина колонок — по содержимому (`table-layout: auto`), без фиксированных `width`: на десктопе 1280 таблица совпадает с контейнером, ячейки не вылезают за свою ширину.

Элементы управления:

- поле поиска `q` (debounce 250 мс, минимум 2 символа);
- фильтры `type` (справочник типов по группам, §2.7), `criticality`, `status` (жизненный цикл), `process_owner`, `site`;
- переключатель «показать архивные»;
- пагинация;
- сортировка по `code`, `name`, `criticality`, `lifecycle_status`, `next_review_at`, `updated_at`;
- кнопки выгрузки XLSX и PDF — для всех четырёх ролей;
- кнопка «Создать систему» — только admin и editor.

Состояние фильтров живёт в query string и шарится ссылкой. Фильтры комбинируются по И. Архивные скрыты, пока `archived=1` не задан.

Пустой реестр и пустой поиск — разные empty-тексты (URS-016).

Строка ведёт на SCR-CARD. `viewer` и `auditor` не видят действий изменения.

### 2.3. SCR-CARD — Карточка системы

Отображает все атрибуты `systems` из раздела 5 контекста плюс ФИО владельца процесса, владельца системы и владельца качества (если задан). Код системы — заголовок, копируется как текст, не редактируется.

Действия по ролям:

- admin, editor: «Изменить», «Архивировать» или «Восстановить»;
- admin: дополнительно может менять `validation_status` на форме редактирования;
- viewer, auditor: только просмотр и выгрузка текущего среза (выгрузка с `id` в фильтре не обязательна; достаточно общей выгрузки).

Архивирование и восстановление открывают диалог обязательной причины (`reason`). Без причины кнопки подтверждения неактивны, сервер всё равно проверяет.

Блок «История изменений» — лента событий аудита именно этой записи (`entity_type = systems`, `entity_id` карточки), от новых к старым. Поля ленты: дата и время (`occurred_at`, UTC, формат ru-RU), актор (логин и роль на момент события), действие, изменённые поля, «Было» / «Стало», причина, идентификатор запроса. Постранично по 50 записей (`page` / `pageSize`, как в остальных списках). Для `create` и любого успешного события с `before = null` блок «Изменённые поля» не перечисляет атрибуты снимка: показывается строка «Создана новая запись», полный состав записи — в «Стало». Для `update`, `archive`, `restore`, `role_change`, `deactivate` и прочих изменений список полей сохраняется. Отказы с пустым `changed_fields` показывают «—». Служебные метки `created_at`, `updated_at`, `archived_at` («Создана», «Изменена», «Дата архивации») в список изменённых полей не входят. Состояния: loading, empty («Изменений пока нет»), error, нет прав. Отказы (события с кодом отказа в `after`) помечены отдельно от успешных изменений. Архивная карточка показывает историю так же, как действующая. IP-адрес и User-Agent в карточке не показываются — они принадлежат инспекторскому экрану журнала (SCR-AUDIT). Лента показывает изменения самой записи, включая отказы; чтение журнала и чтение истории в ленту не входят, они видны в общем журнале.

История — выборка из `audit_events`, не отдельная таблица и не кэш. Формат события тот же, что у общего журнала.

### 2.4. SCR-NEW и SCR-EDIT — Создание и редактирование

Общие поля формы:

| Поле | Обязательность | Валидация |
|---|---|---|
| `name` | да | непустая строка после trim, до 500 символов |
| `vendor` | нет | до 200 символов |
| `product_version` | нет | до 100 символов |
| `description` | нет | текст |
| `system_type` | да | enum, фиксированный справочник §2.7 |
| `business_process` | нет | текст |
| `process_owner_id` | да | UUID активного пользователя |
| `system_owner_id` | да | UUID активного пользователя |
| `quality_owner_id` | нет | UUID активного пользователя или пусто |
| `site` | нет | текст |
| `hosting_type` | да | enum |
| `hosting_provider` | нет, рекомендуется при `cloud` | текст; сервер не отвергает пустое, предупреждение в UI |
| `data_classification` | да | enum |
| `is_gxp_relevant` | да | boolean |
| `criticality` | да | enum |
| `lifecycle_status` | да | enum |
| `validation_status` | да при создании; смена — только admin | enum |
| `validated_at` | нет | дата; логический контроль: при `validated` UI предупреждает, если дата пуста, сервер не блокирует (не зафиксировано в контексте) |
| `next_review_at` | нет | дата |
| `auth_model` | нет | текст |
| `backup_rpo_hours` | нет | целое ≥ 0 |
| `backup_rto_hours` | нет | целое ≥ 0 |
| `notes` | нет | текст |
| `version` | только edit | целое, обязателен в PATCH |
| `reason` | условно | см. раздел 7 |

`code` на создании не вводится: сервер генерирует `SYS-NNNN`. На редактировании поле только для чтения.

Серверная валидация владельцев (URS-090, URS-091, URS-092): `process_owner_id` и `system_owner_id` обязательны, каждый — UUID существующего активного пользователя. Отсутствие любого из двух при POST и PATCH — HTTP 422, `code = OWNERS_REQUIRED`, сущность не пишется, в `audit_events` — событие отказа с тем же `request_id`. Неизвестный или неактивный UUID — 400 `VALIDATION_ERROR`, строка не создаётся. `quality_owner_id` необязателен; пустое значение допустимо; если передан — тот же контроль UUID активного пользователя.

Критичные поля (`criticality`, `is_gxp_relevant`, `validation_status`) и любая правка валидированной системы показывают обязательное поле причины.

Конфликт `version`: сообщение «Запись изменена другим пользователем», предложение перечитать карточку. Код API 409.

Состояния формы: loading при загрузке справочника пользователей и карточки; error при сбое загрузки; нет прав, если `viewer` открыл `/edit` напрямую.

### 2.5. SCR-AUDIT — Журнал аудита

Таблица: `occurred_at` (UTC, отображение в локали ru-RU с пометкой UTC), `actor_username`, `actor_role`, `action`, `entity_type`, `entity_label`, `reason`, `request_id`. Колонка снимков «Было / Стало» имеет минимальную ширину; текст переносится по словам, без разрыва подписей полей посередине. Вывод снимка — человекочитаемые подписи, не технические имена колонок.

Раскрытие строки: `changed_fields`, JSON `before`/`after`, `ip`, `hash` (для сверки, не для редактирования).

Фильтры: период дат, актор (id или username), тип объекта, объект (текстовый поиск по `entity_label`: код `SYS-NNNN` и наименование, без учёта регистра, частичное совпадение), действие. Параметр API `entityId` сохраняется для программных переходов и в интерфейсе не показывается. Пагинация обязательна: журнал не грузится целиком.

Журнал по умолчанию от новых к старым. Направление переключается («Сначала новые» / «Сначала старые»); выбор живёт в query string как `order` (`newest` | `oldest`, по умолчанию `newest`) и уходит в API. Неизвестное значение — 400 `VALIDATION_ERROR`.

Каждое открытие страницы и каждый запрос списка пишут `read_audit`. Повтор фильтра — новое событие чтения: чтение журнала само аудируется.

`editor` и `viewer` при прямом заходе видят «нет прав».

### 2.6. SCR-USERS — Пользователи

Доступ: только `admin`. Список: `username`, `full_name`, `email`, `role`, `is_active`, `last_login_at`.

Создание: `username` (нормализуется в нижний регистр), `full_name`, `email` (уникальный), `password` ≥ 12, `role`.

Изменение: роль, активность, сброс пароля администратором. Смена роли и деактивация требуют `reason`. Нельзя деактивировать или сменить роль последнего активного admin.

Секреты: `password_hash` и `mfa_secret` не отображаются.

Empty: «Нет учётных записей» недостижимо в нормальной поставке (есть первый admin); если список пуст — error-состояние целостности, не empty.

### 2.7. Справочник типов компьютеризированных систем

`system_type` — фиксированный справочник приложения, не редактируемый пользователем. Изменение состава — только через изменение требований (URS) и миграцию PostgreSQL `system_type_enum`. Существующие коды (`LIMS`, `ERP`, `MES`, `QMS`, `SCADA`, `DMS`, `EDC`, `other`) не переименовываются и не удаляются: снимки `audit_events.before` / `after` хранят строковый код.

Группировка — представление форм и фильтра, не колонка БД. `other` стоит последним и вне групп. В селектах создания, редактирования и фильтра списка значения показаны по группам (`optgroup`); текст опции — `КОД — полное название` (например `WMS — Управление складом`). В таблице списка, карточке системы и PDF колонка «Тип» показывает только короткую метку: код (`LIMS`, `WMS`, `LEGAL`) либо «Прочее» для `other`.

## 3. API

Публичного API нет. Все методы раздела 10, кроме login, требуют сессию. Каждый ответ несёт `X-Request-Id`. Тела ошибок:

```json
{ "code": "REASON_REQUIRED", "message": "Для этого изменения нужна причина", "requestId": "…" }
```

Без stack trace, без SQL, без путей сервера.

### 3.1. Коды ошибок

| `code` | HTTP | Когда |
|---|---|---|
| `UNAUTHORIZED` | 401 | нет или недействительна сессия |
| `FORBIDDEN` | 403 | роль не позволяет действие |
| `VALIDATION_ERROR` | 400 | схема Zod, неизвестный enum, короткий пароль |
| `REASON_REQUIRED` | 422 | критичное изменение без непустого `reason` |
| `OWNERS_REQUIRED` | 422 | нет `process_owner_id` или `system_owner_id` при создании или сохранении |
| `NOT_FOUND` | 404 | нет сущности с данным id, в том числе архивная скрыта только из списка, не из GET по id |
| `CONFLICT` | 409 | уникальность `username`/`email`/`code` |
| `VERSION_CONFLICT` | 409 | устаревший `version` при PATCH |
| `LAST_ADMIN` | 409 | попытка убрать последнего активного admin |
| `RATE_LIMITED` | 429 | лимит Caddy или приложения |
| `AUTH_LOCKED` | 423 | временная блокировка входа после 5 неудач |
| `INTERNAL_ERROR` | 500 | непредвиденный сбой; клиенту только `message` общего вида и `requestId` |

HTTP 423 для блокировки входа — решение спецификации: отличить от неверного пароля (401 с тем же текстом, что и обычный отказ) нельзя по сообщению, но код позволяет e2e отличить политику блокировки. Тело всё равно `{ code, message, requestId }`.

### 3.2. Методы

| Метод | Назначение | admin | editor | viewer | auditor | Успех | Типичные ошибки |
|---|---|---|---|---|---|---|---|
| `POST /api/v1/auth/login` | вход | — | — | — | — | 200 + Set-Cookie | 400, 401, 423, 429 |
| `POST /api/v1/auth/logout` | выход | да | да | да | да | 204 | 401 |
| `GET /api/v1/systems` | список, поиск, фильтры | да | да | да | да | 200 | 401, 400, 429 |

### 3.3. Тела запросов (сжато)

`POST /api/v1/systems` — атрибуты карточки без `id`, `code`, `archived_at`, `version`. Сервер выставляет `code`, `version = 1`.

`PATCH /api/v1/systems/:id` — частичный объект плюс обязательный `version`; `reason` обязателен по разделу 7.

`POST archive` / `restore` — `{ "reason": "…" }`.

`GET /api/v1/systems` — query: `q`, `type`, `criticality`, `status`, `process_owner`, `site`, `archived`, `page`, `pageSize`, `sort`, `order`. `process_owner` — UUID владельца процесса.

`GET /api/v1/audit` — query: `from`, `to`, `actor`, `entityType`, `entityLabel`, `entityId`, `action`, `order`, `page`, `pageSize`. `entityLabel` — подстрока `entity_label` без учёта регистра (`ILIKE`, литералы `%` и `_` экранируются). `entityId` — точное совпадение служебного ключа, только API. `order` — `newest` | `oldest`, по умолчанию `newest` (от новых к старым). Неизвестное значение — 400 `VALIDATION_ERROR`.

`GET /api/v1/systems/:id/history` — query: `page`, `pageSize`; ответ `{ items, page, pageSize, total }`. Сортировка строго `id DESC`. Фильтр фиксирован: `entity_type = systems` и `entity_id` из пути. Неизвестный `:id` — 404. Архивная система историю отдаёт.

`POST /api/v1/users` — `{ username, full_name, email, password, role }`.

`PATCH /api/v1/users/:id` — любое из `role`, `is_active`, `password`, `full_name`, `email` плюс `reason` при смене роли или деактивации.

## 4. Пагинация, сортировка, семантика поиска

Пагинация списков систем, аудита и пользователей:

- `page` — натуральное число, по умолчанию 1;
- `pageSize` — по умолчанию 50, максимум 100;
- ответ: `{ items, page, pageSize, total }`.

Сортировка систем: `sort` из белого списка `code | name | criticality | lifecycle_status | next_review_at | updated_at`, `order` = `asc | desc`. По умолчанию `code asc`. Неизвестный `sort` — 400 `VALIDATION_ERROR`.

Сортировка журнала аудита: `order` = `newest | oldest`, по умолчанию `newest`. Page=1 при `newest` содержит наибольшие `id`, при `oldest` — наименьшие. Неизвестный `order` — 400 `VALIDATION_ERROR`.

Поиск (`q`):

1. Длина меньше 2 — параметр игнорируется, возвращается выборка только по фильтрам (на клиенте запрос с одним символом не отправляется).
2. Debounce 250 мс, `AbortController` отменяет предыдущий запрос.
3. SQL: `unaccent(lower(поле))` и сходство/`LIKE` по `pg_trgm` для подстроки.
4. Приоритет ранжирования: точное совпадение `code` (без учёта регистра), затем начало `name`, затем подстрока по `name` / `vendor` / `code`.
5. Фильтры после поиска применяются по И.
6. Целевой P95 < 200 мс на 5 000 записей — качество Should, не ломает контракт.

Выгрузка использует те же фильтры и `q`, что список, и **игнорирует пагинацию**: в файл попадает полный срез выборки. Верхняя граница объёма — расчётные 5 000 строк; отдельный лимит «не больше N» контекстом не задан.

## 6. Формат события аудита

Запись создаётся только модулем `audit` через репозиторий. Поля:

| Поле | Тип | Кто заполняет | Содержание |
|---|---|---|---|
| `id` | bigserial | БД | монотонный PK |
| `occurred_at` | timestamptz | БД `now()` | никогда из клиента |
| `actor_id` | uuid, null | модуль | пользователь; null у системных событий |
| `actor_username` | text | модуль | снимок логина или `system` |
| `actor_role` | text | модуль | снимок роли или `system` |
| `action` | text | модуль | `create`, `update`, `archive`, `restore`, `activate`, `deactivate`, `login`, `login_failed`, `logout`, `role_change`, `password_reset`, `export`, `read_audit`, `read_system_history` |
| `entity_type` | text | модуль | `systems`, `users`, `auth` |
| `entity_id` | text, null | модуль | id объекта строкой; null, если объекта нет |
| `entity_label` | text, null | модуль | `code`+`name` системы, `username` пользователя, иначе null |
| `changed_fields` | text[], null | сериализатор | имена изменённых полей |
| `before` | jsonb, null | сериализатор | только изменённые поля, прежние значения |
| `after` | jsonb, null | сериализатор | только изменённые поля, новые значения |
| `reason` | text, null | модуль | см. раздел 7 |
| `request_id` | text | HTTP-адаптер | равен `X-Request-Id` |
| `ip` | inet, null | HTTP-адаптер | адрес клиента |
| `user_agent` | text, null | HTTP-адаптер | заголовок UA |
| `prev_hash` | text, null | модуль audit | `hash` предыдущей строки; null у первой |
| `hash` | text | модуль audit | SHA-256 канонической сериализации полей записи без самого `hash`, плюс `prev_hash` |

### 6.1. Что попадает в `before` / `after`

Включаются только фактически изменившиеся колонки сущности. Не включаются никогда:

- `password_hash`, `mfa_secret`, открытый пароль, токен сессии;
- служебные `updated_at` допускается включить, если значение изменилось, но не вместо смысловых полей;
- полный снимок неизменённых колонок.

Примеры:

- смена `criticality` medium → high: `changed_fields = [criticality]`, `before = {"criticality":"medium"}`, `after = {"criticality":"high"}`;
- создание системы: `before = null`, `after` содержит выставленные поля без секретов, включая ФИО владельца процесса и владельца системы на момент события (не пустые строки), `changed_fields` — список созданных атрибутов либо null с заполненным `after` целиком по созданным полям (единый сериализатор выбирает второе: `after` = созданные несекретные поля);
- смена владельца: в `changed_fields` ключ `process_owner_id` / `system_owner_id` / `quality_owner_id`; в `before` и `after` рядом с id лежат соответствующие `*_owner_name` с ФИО на момент события;
- `login` / `logout` / `login_failed`: `before` и `after` null, `entity_type = auth`;
- `export`: `after` = `{ "format": "xlsx"|"pdf", "filters": {…}, "rowCount": N }`, `before` null;
- `read_audit`: `after` = `{ "filters": {…} }` либо null, без содержимого прочитанных событий;
- `read_system_history`: `entity_type = systems`, `entity_id` карточки; `after` = `{ "page", "pageSize" }` либо фильтры выборки, без содержимого ленты;
- `activate` / `deactivate` относятся только к учётным записям (`entity_type = users`, поле `is_active`). Архив и возврат систем — это `archive` / `restore`, не `activate` / `deactivate`;
- `password_reset`: администратор сменил пароль учётки; в `before`/`after` нет `password_hash`, открытого пароля и `mfa_secret`;
- `role_change`: смена `users.role`;
- отказ (403, 422): событие с `action` исходного намерения либо `login_failed`; в `after` код отказа (`FORBIDDEN`, `REASON_REQUIRED`). Успешного изменения сущности нет.

Каноническая сериализация для `hash` — стабильный JSON с отсортированными ключами, UTF-8, без пробелов. Алгоритм SHA-256. Первая запись: `prev_hash` null, в хеш входит фиксированный соль-префикс `genesis`, чтобы не хешировать пустую строку неоднозначно.

## 7. Правило `reason`

Непустое `reason` (после trim длина ≥ 1) обязательно, если выполняется любое из условий:

1. Изменяется `systems.validation_status`.
2. Изменяется `systems.criticality`.
3. Изменяется `systems.is_gxp_relevant`.
4. Выполняется архивирование (`archived_at` с null на значение).
5. Выполняется восстановление (`archived_at` на null).
6. Изменяется `users.role`.
7. Пользователь деактивируется (`is_active` true → false).
8. Выполняется любое редактирование системы, у которой **текущее** (до PATCH) значение `validation_status = validated`.

Поведение API при отсутствии:

- HTTP **422**, `code = REASON_REQUIRED`;
- сущность не изменяется;
- в `audit_events` пишется событие отказа с тем же `request_id`, актором, `entity_id` и пустым либо отсутствующим `reason`, чтобы Complete-след остался.

Пробельная строка приравнивается к отсутствию. Для некритичных PATCH `reason` необязателен; если передан — сохраняется в событии.

Смена статуса валидации дополнительно требует роль `admin`. Если `editor` присылает и статус, и причину — ответ **403**, не 422: сначала полномочие, потом причина.

## 8. Контракт выгрузок

Общее:

- методы `GET /api/v1/systems/export?format=xlsx|pdf` плюс те же query-фильтры, что у списка;
- формирование на сервере модулем `export`;
- `Content-Disposition: attachment; filename="cs-registry_<YYYY-MM-DD>_<HHMM>_<short-request-id>.<ext>"`, время UTC;
- событие `export` до или в той же транзакции метаданных, что и старт формирования; если формирование падает после события, событие сохраняется с фактическим `rowCount` и не удаляется (журнал append-only);
- состав колонок не шире отображаемого реестра: нет email, паролей, MFA.

### 8.1. XLSX

| Лист | Содержание |
|---|---|
| Реестр | Строки выборки. Первая колонка `code`. Последняя колонка `id` скрыта. Шапка заморожена, автофильтр включён. Даты — ISO 8601. |
| Параметры выгрузки | Актор (username, роль), время формирования UTC, фильтры как пары ключ–значение, число записей, SHA версии приложения, имя файла, `request_id`. |
| Справочники | Таблица enum: поле, значение (код), расшифровка (полное название), группа. Группа заполнена только для `system_type` (кроме `other`). Первые три колонки — прежний контракт; четвёртая — расширение без ломки. |

Русские расшифровки справочника — часть контракта выгрузки, чтобы файл читался без системы.

### 8.2. PDF

- Титульная страница: заголовок «Реестр компьютеризированных систем», период/фильтры, актор, время формирования UTC, SHA версии, идентификатор отчёта (= `request_id`).
- Таблица записей, шапка повторяется на каждой странице, нумерация «страница X из Y».
- Колонтитул каждой страницы: идентификатор отчёта и время формирования.
- Шрифт с кириллицей встраивается в файл.

Неизвестный `format` — 400 `VALIDATION_ERROR`.

## 9. Целостность поставки и границы объёма

Поведение, которое не принадлежит одному экрану, но входит в контракт поставки.

**Транзакция данных и аудита.** Модуль, изменяющий `systems` или `users`, вызывает `audit` в той же транзакции БД. Сбой на любом шаге откатывает и данные, и событие. Успешная мутация не существует без строки `audit_events`.

**Один тенант.** Переключателя организаций нет. Уникальность `systems.code`, `users.username` и `users.email` — глобальная. Колонка `tenant_id` в этом объёме не вводится, чтобы не притворяться мультитенантностью; добавление её — отдельная миграция, не запрещённая текущими ключами.

**Защита журнала.** Прикладная роль БД без `UPDATE`/`DELETE` на `audit_events`; триггер `BEFORE UPDATE OR DELETE` поднимает исключение. Проверка хеш-цепочки — задание `pnpm audit:verify` (`scripts/verify-audit-chain.ts`): успех печатает «Цепочка цела» и код 0, разрыв — номер записи, причину и код 1 (URS-041, URS-099). Ежедневная контрольная точка (`id`, `hash`) пишется атомарно в файл `AUDIT_CHECKPOINT_FILE` вне доступа прикладной роли; расхождение с предыдущей точкой — отказ (URS-044, URS-100). Пример cron и systemd — `docs/operations/audit-verify.md`.

**Резервное копирование.** URS-070 и URS-071 — требования к системе целиком, не к объёму первого релиза. В MVP входит: скрипт/задание ежедневного логического дампа, шифрование до отправки, документированная процедура восстановления, проверенная минимум один раз до демонстрации; ротация 7 дневных / 4 недельных / 6 месячных; RPO 24 ч, RTO 4 ч. Срок хранения сверх этой ротации не зафиксирован (открытый вопрос, решение отложено 29.10.2026). Мажор клиента `pg_dump`/`pg_restore` должен совпадать с сервером: клиент 17 против PostgreSQL 16 дописывает `SET transaction_timeout = 0`, и `pg_restore --exit-on-error` падает на первой строке; иначе — plain-дамп с вырезанной строкой. Процедура — `docs/operations/backup-restore.md`. Вне кода приложения (эксплуатация и ввод в эксплуатацию): провижининг S3-совместимого бакета, управление ключами шифрования, политики жизненного цикла хранения.

**CI-гейт.** Lint, typecheck, unit, integration, build — `.github/workflows/ci.yml` (Node 22, pnpm 10, job `integration` с `postgres:16` и `TEST_DATABASE_URL`). Репозиторий в Cursor Origin, GitHub Actions не исполняет файл. Предполётная проверка — `pnpm ci:local` (URS-101).

**Изоляция тестовой БД.** Интеграционные и e2e-тесты читают только `TEST_DATABASE_URL` / `TEST_DATABASE_ADMIN_URL`. Совпадение с `DATABASE_URL` или отсутствие переменной — отказ на старте с русским сообщением, сценарии не выполняются. Setup делает `TRUNCATE` `sessions`, `systems`, `users`, `audit_events`; row-триггер журнала TRUNCATE не блокирует (URS-102).

**E2E критический путь.** Playwright (`pnpm e2e`, `e2e/critical-path.spec.ts`) против `pnpm start` и тестовой базы: вход → создание системы → поиск → правка с причиной → журнал аудита → история в карточке (URS-103).

**Канал доступа.** Внешний вход только HTTPS через Caddy, security headers на edge, rate limit на login и (Should) на поиск. Длительность сессии по ролям: `admin` — 30 минут (`SESSION_MINUTES_ADMIN`), остальные роли — 10 минут (`SESSION_MINUTES_DEFAULT`). Cookie `sid` получает соответствующий `Max-Age` (1800 / 600 секунд).

**Хранение аудита.** Журнал хранится бессрочно; прикладной API не удаляет записи (URS-038, решение заказчика 29.10.2026).

**Логи.** pino, correlation ID = `X-Request-Id`. Запрещены пароль, токен, `password_hash`, `mfa_secret`, email и тела карточек.

**Восстановление пароля.** Восстановление по SMTP в MVP не входит; пароль сбрасывает администратор вручную (URS-065, решение заказчика 29.10.2026). Эндпоинтов SMTP в API нет.

**Категория GAMP и роли валидации.** Категория GAMP 5 — 5, заказная разработка (URS-096). Владелец системы в смысле валидации — заказчик: жизненный цикл и валидационный статус, тест-кейсы и документация. Исполнители валидации — отдельные люди, пока не назначены. Владелец процесса в терминах реестра — заказчик. Площадки и подразделения: заказчик, Качество, ИТ (URS-097).

**Part 11, что вне кода.** ЭП не требуется (решение заказчика 29.10.2026). `reason` и снимок актора остаются атрибуцией действий. 11.10(i) закрыт отсутствием публичного API. 11.10(j) и (k) — обучение и политики вне системы. Комплект `docs/validation/` поставляется отдельными документами; до подписи человеком статус — «готово к демонстрации», не «валидировано». `mfa_secret` допускает null, второй фактор во вход не входит.

## 10. Трассировка FS → URS

Сначала разделы FS против требований, затем полный перечень URS. Многоточия в идентификаторах не используются.

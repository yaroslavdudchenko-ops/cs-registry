# Пользовательские требования (URS)

Источник правды: `docs/INITIAL-CONTEXT.md` v0.2.0. Каждое требование имеет критерий приёмки. Приоритет **Must** покрывает весь MVP раздела 3 контекста и критерии готовности раздела 11. **Should** — целевые метрики и качество, без которых демонстрация возможна. **Could** — зафиксированные ограничения и заделы вне реализации демо.

Идентификаторы стабильны: новые требования получают следующий свободный номер, существующие не перенумеровываются.

Категория GAMP 5 — **5** (заказная разработка). ЭП не требуется (решение заказчика 29.10.2026).

## Ведение реестра

### URS-001 — Список систем
**Требование.** Система должна показывать аутентифицированному пользователю список компьютеризированных систем с кодом, наименованием, типом, критичностью, статусом жизненного цикла, владельцем процесса и площадкой.
**Источник.** Раздел 3 контекста, пункт 1 / все роли.
**Критерий приёмки.** После входа пользователь с правом просмотра видит таблицу систем, у каждой строки заполнены `code`, `name`, `system_type`, `criticality`, `lifecycle_status`, ФИО владельца процесса и `site`; архивные записи в основном списке отсутствуют.
**Приоритет.** Must

### URS-002 — Карточка системы
**Требование.** Система должна открывать карточку выбранной системы со всеми атрибутами раздела 5 контекста, кроме секретов.
**Источник.** Раздел 3 контекста, пункт 1 / раздел 5.
**Критерий приёмки.** По `GET` карточки возвращаются все колонки `systems` и отображаемые ФИО владельца процесса, владельца системы и владельца качества (если задан); `password_hash` и `mfa_secret` в ответе отсутствуют.
**Приоритет.** Must

### URS-003 — Создание системы
**Требование.** Система должна позволять ролям `admin` и `editor` создать запись реестра с генерацией неизменяемого кода `SYS-NNNN`.
**Источник.** Раздел 3 контекста, пункт 1 / роли admin, editor / раздел 5 `systems.code`.
**Критерий приёмки.** Успешный POST создаёт запись, код уникален и соответствует шаблону `SYS-` плюс десятичные цифры; повторный POST не переиспользует код; в аудите есть событие `create`.
**Приоритет.** Must

### URS-004 — Редактирование системы
**Требование.** Система должна позволять ролям `admin` и `editor` изменять разрешённые поля существующей записи с оптимистичной блокировкой по `version`.
**Источник.** Раздел 3 контекста, пункт 1 / раздел 5 `version`.
**Критерий приёмки.** PATCH с актуальным `version` сохраняет поля и увеличивает `version` на 1; PATCH с устаревшим `version` отклоняется с конфликтом и не меняет строку.
**Приоритет.** Must

### URS-005 — Архивирование системы
**Требование.** Система должна позволять ролям `admin` и `editor` архивировать запись: запись скрывается из основного списка, не удаляется физически.
**Источник.** Раздел 3 контекста, пункт 1 / раздел 5 `archived_at` / раздел 9a критичные изменения.
**Критерий приёмки.** POST archive при непустом `reason` ставит `archived_at`, запись исчезает из основного списка, доступна по прямой ссылке или фильтру архива, в аудите событие `archive` с причиной.
**Приоритет.** Must

### URS-006 — Восстановление из архива
**Требование.** Система должна позволять ролям `admin` и `editor` восстановить архивную запись в основной список.
**Источник.** Раздел 10 API `restore` / раздел 9a.
**Критерий приёмки.** POST restore при непустом `reason` обнуляет `archived_at`, запись снова видна в основном списке, в аудите событие `restore`.
**Приоритет.** Must

### URS-007 — Неизменяемость кода
**Требование.** Система не должна принимать изменение `systems.code` после создания.
**Источник.** Раздел 5 контекста, `code` неизменяем.
**Критерий приёмки.** PATCH, содержащий `code`, отклоняется; значение в БД совпадает с исходным.
**Приоритет.** Must

### URS-008 — Состав атрибутов карточки
**Требование.** Система должна хранить и отображать атрибуты системы, перечисленные в разделе 5: тип, вендор, версия продукта, процесс, владелец процесса, владелец системы, владелец качества, площадка, хостинг, классификация данных, GxP-релевантность, критичность, жизненный цикл, статус валидации, даты валидации и переоценки, модель аутентификации, RPO/RTO, примечания.
**Источник.** Раздел 5 `systems`.
**Критерий приёмки.** Для каждого поля раздела 5 существует ввод или отображение; недопустимое значение перечисления отклоняется до записи.
**Приоритет.** Must

### URS-009 — Обязательные поля создания
**Требование.** Система должна требовать при создании непустое `name`, допустимые значения перечислений `system_type`, `hosting_type`, `data_classification`, `criticality`, `lifecycle_status`, `validation_status`, булево `is_gxp_relevant` и существующих активных `process_owner_id` и `system_owner_id`.
**Источник.** Раздел 5 / ведение реестра / URS-090.
**Критерий приёмки.** Запрос без `name` или с неизвестным `process_owner_id` или `system_owner_id` возвращает ошибку валидации и не создаёт строку.
**Приоритет.** Must

### URS-010 — Архивные записи скрыты по умолчанию
**Требование.** Основной список не должен включать записи с заполненным `archived_at`, пока пользователь явно не запросил архив.
**Источник.** Раздел 5 `archived_at`.
**Критерий приёмки.** GET списка без параметра архива не содержит архивных `id`; при явном параметре архивные строки возвращаются.
**Приоритет.** Must

### URS-011 — Запрет физического удаления системы
**Требование.** Система не должна предоставлять операцию физического удаления записи реестра.
**Источник.** Раздел 3 (архивирование вместо удаления) / ALCOA+ Original.
**Критерий приёмки.** В API нет DELETE `/systems/:id`; попытка удалить строку через прикладную роль не предусмотрена контрактом и не выполняется сценарием UI.
**Приоритет.** Must

## Поиск и фильтры

### URS-012 — Живой поиск
**Требование.** Система должна обновлять список систем по мере ввода запроса без перезагрузки страницы.
**Источник.** Раздел 3, пункт 2 / раздел 8.
**Критерий приёмки.** Ввод в поле поиска инициирует запрос к API и заменяет строки списка без полной перезагрузки документа.
**Приоритет.** Must

### URS-013 — Минимальная длина и debounce
**Требование.** Поиск должен отправляться при длине запроса не менее 2 символов и не чаще, чем с задержкой 250 мс после последнего ввода; предыдущий незавершённый запрос отменяется.
**Источник.** Раздел 8.
**Критерий приёмки.** Один символ не вызывает поисковый запрос; после паузы ≥ 250 мс уходит один запрос с актуальным текстом; отменённый запрос не перезаписывает более новый результат.
**Приоритет.** Must

### URS-014 — Фильтры реестра
**Требование.** Система должна фильтровать список по типу, критичности, статусу жизненного цикла, владельцу процесса и площадке.
**Источник.** Раздел 3, пункт 2 / раздел 8.
**Критерий приёмки.** Установка каждого фильтра по отдельности оставляет в выборке только строки с совпадающим значением; несовпадающие отсутствуют.
**Приоритет.** Must

### URS-015 — Комбинация фильтров и состояние в URL
**Требование.** Фильтры и строка поиска должны комбинироваться по логическому И, а состояние — сериализоваться в URL, чтобы ссылка воспроизводила ту же выборку.
**Источник.** Раздел 8.
**Критерий приёмки.** Одновременные `q`, `type` и `criticality` возвращают пересечение условий; открытие сохранённого URL восстанавливает те же параметры и тот же набор `id`.
**Приоритет.** Must

### URS-016 — Пустой результат поиска
**Требование.** Система должна показывать явное состояние «ничего не найдено» с действием сбросить фильтры, а не пустую страницу без пояснения.
**Источник.** Раздел 8.
**Критерий приёмки.** При нуле строк список заменяется текстом об отсутствии результатов и элементом сброса; элемент сброса очищает `q` и фильтры.
**Приоритет.** Must

### URS-017 — Ранжирование поиска
**Требование.** Система должна отдавать приоритет точному совпадению по `code`, затем совпадению по началу `name`, затем подстроке.
**Источник.** Раздел 8 / задание на спецификацию.
**Критерий приёмки.** При данных `SYS-0001` «Альфа» и `SYS-0010` «Система Альфа-тест» запрос `SYS-0001` ставит точный код первым; запрос `Альф` ставит «Альфа» выше записи, где совпадение не в начале.
**Приоритет.** Must

### URS-018 — Русский и латинский поиск
**Требование.** Поиск должен находить записи по кириллице и латинице в наименованиях и вендорах с нормализацией `unaccent` и триграммами `pg_trgm`.
**Источник.** Допущение A-3 / раздел 8.
**Критерий приёмки.** Запрос без диакритики находит вендора с диакритикой; запрос кириллицей находит кириллическое `name`; сравнение выполняется без учёта регистра.
**Приоритет.** Must

### URS-019 — Целевое время поиска
**Требование.** Система должна отвечать на поиск с P95 менее 200 мс на объёме 5 000 записей.
**Источник.** Раздел 8, целевые метрики.
**Критерий приёмки.** На стенде с 5 000 систем измеренный P95 latency `GET /api/v1/systems?q=` строго меньше 200 мс.
**Приоритет.** Should

## Ролевая модель и доступ

### URS-020 — Четыре роли, одна на пользователя
**Требование.** Система должна назначать пользователю ровно одну роль из `admin`, `editor`, `viewer`, `auditor`.
**Источник.** Раздел 6.
**Критерий приёмки.** Создание пользователя с двумя ролями или с неизвестной ролью отклоняется; в БД хранится одно значение `role`.
**Приоритет.** Must

### URS-021 — Серверная проверка прав
**Требование.** Система должна проверять полномочия на сервере при каждом защищённом действии; скрытие кнопки в интерфейсе не является единственной защитой.
**Источник.** Раздел 3, пункт 3 / раздел 6 / Part 11 §11.10(d).
**Критерий приёмки.** Запрос `viewer` на POST `/api/v1/systems` с валидным телом возвращает 403 и не создаёт запись даже при ручном вызове API.
**Приоритет.** Must

### URS-022 — Запрет по умолчанию
**Требование.** Любое действие, не разрешённое матрице ролей, должно быть запрещено.
**Источник.** Раздел 6, принцип «запрещено по умолчанию».
**Критерий приёмки.** Для каждой ячейки «нет» матрицы раздела 6 соответствующий API-вызов роли даёт 403.
**Приоритет.** Must

### URS-023 — Права администратора
**Требование.** Роль `admin` должна просматривать реестр, создавать и редактировать системы, архивировать, менять статус валидации, просматривать аудит, выгружать данные и управлять пользователями и ролями. Администратор не должен изменять или удалять записи аудита.
**Источник.** Раздел 6, роль admin.
**Критерий приёмки.** Набор разрешённых API для `admin` совпадает с матрицей FS; прямой UPDATE/DELETE в `audit_events` прикладной ролью БД невозможен.
**Приоритет.** Must

### URS-024 — Права редактора
**Требование.** Роль `editor` должна вести записи реестра (создание, редактирование, архивирование, восстановление, выгрузка) и не должна менять статус валидации, управлять пользователями и читать аудит-трейл.
**Источник.** Раздел 6, роль editor.
**Критерий приёмки.** PATCH `validation_status` от `editor` даёт 403; GET `/api/v1/audit` даёт 403; POST `/api/v1/users` даёт 403; POST системы — 201.
**Приоритет.** Must

### URS-025 — Права наблюдателя
**Требование.** Роль `viewer` должна читать реестр и выгружать срез и не должна изменять данные, читать аудит и управлять пользователями.
**Источник.** Раздел 6, роль viewer.
**Критерий приёмки.** GET списка — 200; PATCH системы, GET аудита, POST пользователя — 403.
**Приоритет.** Must

### URS-026 — Права аудитора
**Требование.** Роль `auditor` должна читать реестр, аудит-трейл и выгружать срез и не должна выполнять никаких записывающих операций.
**Источник.** Раздел 6, роль auditor.
**Критерий приёмки.** GET систем и GET аудита — 200; POST/PATCH/archive/restore/users POST и PATCH — 403.
**Приоритет.** Must

### URS-027 — Нет публичной регистрации
**Требование.** Система не должна предоставлять публичную саморегистрацию; учётную запись создаёт только `admin`.
**Источник.** Раздел 6, правила.
**Критерий приёмки.** Неаутентифицированный POST `/api/v1/users` возвращает 401; в маршрутах нет публичной формы регистрации.
**Приоритет.** Must

### URS-028 — Последний активный администратор
**Требование.** Система не должна деактивировать или понижать роль последнего активного пользователя с ролью `admin`.
**Источник.** Раздел 6, правила.
**Критерий приёмки.** Когда в БД ровно один `role = admin` и `is_active = true`, PATCH деактивации или смены роли этого пользователя возвращает ошибку и не меняет строку.
**Приоритет.** Must

### URS-029 — Смена статуса валидации только администратором
**Требование.** Изменять `systems.validation_status` должен только `admin`, с непустой причиной.
**Источник.** Раздел 6 / раздел 9a / Part 11 §11.10(f).
**Критерий приёмки.** `editor` получает 403; `admin` без `reason` получает ошибку причины; `admin` с `reason` меняет статус, в аудите есть `reason`.
**Приоритет.** Must

### URS-030 — Совмещение auditor и admin
**Требование.** Система должна хранить одну роль на пользователя и тем самым не совмещать `auditor` и `admin` в одной учётке.
**Источник.** Раздел 6, замечание о несовмещении ролей.
**Критерий приёмки.** Невозможно сохранить пользователю одновременно две роли; смена `admin` → `auditor` пишет событие `role_change` с причиной.
**Приоритет.** Must

## Аудит и история

### URS-031 — Неизменяемая запись об изменениях
**Требование.** Система должна записывать в `audit_events` каждое создание, изменение, архивирование и восстановление в той же транзакции, что и изменение данных.
**Источник.** Раздел 3, пункт 4 / раздел 7 Accurate / критерий готовности 3.
**Критерий приёмки.** Успешный PATCH системы даёт ровно одно новое событие с тем же `request_id`; откат транзакции изменения не оставляет события; UPDATE/DELETE по `audit_events` невозможны.
**Приоритет.** Must

### URS-032 — Неуспешные попытки в аудите
**Требование.** Система должна фиксировать неуспешный вход, отказ в доступе и отказ валидации (включая отсутствие `reason`).
**Источник.** Раздел 7 Complete / критерий готовности 8.
**Критерий приёмки.** Неверный пароль создаёт `login_failed`; 403 на защищённом действии создаёт событие отказа; PATCH без `reason` на критичном поле отклоняется и оставляет событие отказа.
**Приоритет.** Must

### URS-033 — Атрибуция события
**Требование.** Каждое событие должно содержать `actor_id` либо явную пометку системного события, снимок `actor_username` и `actor_role` на момент события.
**Источник.** Раздел 7 Attributable / Part 11 §11.10(e).
**Критерий приёмки.** Событие пользовательского действия имеет непустые `actor_username` и `actor_role`; системное событие имеет `actor_id` null и отличимый `actor_username` (например, `system`).
**Приоритет.** Must

### URS-034 — Читаемые до и после
**Требование.** Поля `changed_fields`, `before` и `after` должны содержать только изменённые поля в человекочитаемом JSON, а не полный дамп строки.
**Источник.** Раздел 7 Legible / раздел 5.
**Критерий приёмки.** При смене только `criticality` в `changed_fields` есть `criticality` и нет неизменённого `name`; `before.criticality` и `after.criticality` заполнены.
**Приоритет.** Must

### URS-035 — Время из базы данных
**Требование.** `occurred_at` должно браться из часов БД в момент транзакции, а не из клиента.
**Источник.** Раздел 7 Contemporaneous / раздел 5.
**Критерий приёмки.** Передача клиентского timestamp в теле запроса игнорируется; `occurred_at` совпадает с `now()` транзакции в UTC.
**Приоритет.** Must

### URS-036 — Исправление как новое событие
**Требование.** Первая запись аудита не должна перезаписываться; исправление данных порождает новое событие.
**Источник.** Раздел 7 Original.
**Критерий приёмки.** Повторный PATCH той же системы увеличивает число строк `audit_events`, не изменяя `hash` предыдущей.
**Приоритет.** Must

### URS-037 — Единый формат события
**Требование.** Все модули должны писать события одним сериализатором и одним набором полей.
**Источник.** Раздел 7 Consistent.
**Критерий приёмки.** События `create` системы, `role_change` и `login` содержат одинаковые обязательные ключи контракта FS; нет модуля с собственным JSON-форматом журнала.
**Приоритет.** Must

### URS-038 — Хранение аудита
**Требование.** Журнал должен сохраняться бессрочно; прикладной API не удаляет записи аудита.
**Источник.** Раздел 7 Enduring. Решение заказчика 29.10.2026: срок хранения аудита — бессрочно.
**Критерий приёмки.** В API нет операции очистки журнала; документированный срок хранения — бессрочно.
**Приоритет.** Must

### URS-039 — Просмотр и фильтры журнала
**Требование.** Система должна показывать журнал с фильтрами по дате, актору, объекту и действию ролям `admin` и `auditor`.
**Источник.** Раздел 7 Available / раздел 3, пункт 4.
**Критерий приёмки.** GET `/api/v1/audit` с каждым из фильтров возвращает только совпадающие события; `editor` получает 403.
**Приоритет.** Must

### URS-040 — Время выборки журнала
**Требование.** Выборка журнала за календарный месяц должна укладываться в P95 менее 1 с.
**Источник.** Раздел 7 Available.
**Критерий приёмки.** На стенде с данными за месяц измеренный P95 GET аудита с фильтром дат строго меньше 1 с.
**Приоритет.** Should

### URS-041 — Хеш-цепочка
**Требование.** Каждая запись аудита должна хранить `prev_hash` и `hash` SHA-256 канонической сериализации записи плюс `prev_hash`; разрыв должен обнаруживаться проверочным заданием.
**Источник.** Раздел 7, техническая защита п.3 / критерий готовности 4.
**Критерий приёмки.** Для записей `id = n` и `n+1` значение `prev_hash` следующей равно `hash` предыдущей; искусственный разрыв задание помечает как нарушение.
**Приоритет.** Must

### URS-042 — Права БД на журнал
**Требование.** Прикладная роль БД не должна иметь `UPDATE` и `DELETE` на `audit_events`.
**Источник.** Раздел 7, техническая защита п.1 / критерий готовности 3.
**Критерий приёмки.** Выполнение UPDATE и DELETE от прикладной роли возвращает отказ привилегий; интеграционный тест это фиксирует.
**Приоритет.** Must

### URS-043 — Триггер защиты журнала
**Требование.** Триггер `BEFORE UPDATE OR DELETE` на `audit_events` должен поднимать исключение даже при ошибке в правах.
**Источник.** Раздел 7, техническая защита п.2.
**Критерий приёмки.** Попытка UPDATE/DELETE от роли с повышенными правами, но через таблицу с триггером, завершается исключением триггера и нулём изменённых строк.
**Приоритет.** Must

### URS-044 — Ежедневная контрольная точка
**Требование.** Ежедневное задание должно записывать последний `id` и `hash` во внешнее хранилище вне доступа прикладной роли.
**Источник.** Раздел 7, техническая защита п.4.
**Критерий приёмки.** После прогона задания во внешнем хранилище есть объект с `id` и `hash`, совпадающими с последней строкой `audit_events`; прикладная роль БД этот объект прочитать не может.
**Приоритет.** Must

### URS-045 — Чтение журнала аудируется
**Требование.** Просмотр аудит-трейла должен сам порождать событие `read_audit`.
**Источник.** Раздел 7, техническая защита п.5 / раздел 5 `action`.
**Критерий приёмки.** GET `/api/v1/audit` добавляет событие `read_audit` с `actor_id` читателя; выборка следующего запроса это событие содержит.
**Приоритет.** Must

### URS-046 — Причина критичного изменения
**Требование.** Система должна требовать непустое `reason` для изменения `validation_status`, `criticality`, `is_gxp_relevant`, архивирования и восстановления, смены роли, деактивации пользователя и любого редактирования системы со `validation_status = validated`.
**Источник.** Раздел 9a / критерий готовности 8.
**Критерий приёмки.** Каждый случай из перечня без `reason` даёт ошибку и не меняет сущность; с непустым `reason` — успех и поле в событии аудита.
**Приоритет.** Must

### URS-047 — Маскирование секретов в аудите
**Требование.** Секреты, хеши паролей и лишние персональные данные не должны попадать в `before`/`after`.
**Источник.** Раздел 5, абзац о сериализаторе.
**Критерий приёмки.** Смена пароля или роли не записывает `password_hash` и `mfa_secret` в JSON аудита; в журнале нет открытого пароля.
**Приоритет.** Must

### URS-048 — Корреляционный идентификатор
**Требование.** Каждое событие аудита и каждый HTTP-ответ должны нести один и тот же `request_id` / `X-Request-Id`.
**Источник.** Раздел 5 `request_id` / раздел 10.
**Критерий приёмки.** Заголовок ответа, тело ошибки и поле `audit_events.request_id` совпадают для одного запроса.
**Приоритет.** Must

### URS-093 — Лог изменений объекта в карточке
**Требование.** Карточка КС должна показывать историю изменений именно этого объекта — все события аудита с `entity_type = systems` и его `entity_id`, от новых к старым, с датой и временем, актором (логин и роль на момент события), действием, изменёнными полями, значениями до и после, причиной и идентификатором запроса; отказы, записанные по этому объекту, показываются в той же ленте с явной пометкой отказа. Лента показывает изменения самой записи, включая отказы; чтение журнала и чтение истории в ленту не входят, они видны в общем журнале.
**Источник.** Раздел 7 ALCOA+ Original/Complete/Available; Part 11 §11.10(e) (аудит-трейл доступен для просмотра по каждой записи).
**Критерий приёмки.** После создания системы, двух правок, архивирования и восстановления два последовательных запроса истории дают одинаковый `total = 5` и одинаковый набор `id`; ни одно событие другого объекта в ленту не попадает; отклонённая попытка PATCH по существующему объекту отображается как отказ.
**Приоритет.** Must

### URS-094 — История объекта как выборка из единого журнала
**Требование.** История объекта не должна храниться в отдельной таблице или копии; это выборка из `audit_events` по `entity_type` и `entity_id`, полученная тем же сериализатором и тем же форматом события, что и общий журнал, без возможности правки и удаления.
**Источник.** Раздел 7 Original/Consistent; URS-037, URS-042, URS-043.
**Критерий приёмки.** В схеме БД нет второй таблицы истории; правка объекта даёт одно событие, которое видно и в карточке, и в общем журнале с совпадающим `id`; UPDATE и DELETE по этому событию невозможны теми же механизмами, что в URS-042 и URS-043.
**Приоритет.** Must

### URS-095 — Полнота покрытия действий пользователя
**Требование.** Каждое действие пользователя, меняющее данные или дающее доступ к защищённым данным, должно оставлять событие в аудите: вход, неудачный вход, выход, создание, изменение, архивирование и восстановление системы, создание и изменение учётной записи, смена роли, деактивация и активация учётки, сброс пароля администратором, выгрузка XLSX и PDF, просмотр журнала, просмотр истории объекта.
**Источник.** Раздел 7 Complete; Part 11 §11.10(e).
**Критерий приёмки.** Интеграционный тест получает перечень защищённых эндпоинтов из той же константы, что использует guard RBAC, вызывает каждый и проверяет появление события с тем же `request_id`; расхождение между перечнем эндпоинтов и перечнем проверяемых событий валит тест.
**Приоритет.** Must

## Выгрузки

### URS-049 — Выгрузка XLSX
**Требование.** Система должна формировать на сервере книгу XLSX: лист «Реестр» с текущим срезом и фильтрами, лист «Параметры выгрузки», лист «Справочники»; `code` — первая колонка, `id` — последняя скрытая.
**Источник.** Раздел 9c / A-1.2 / Part 11 §11.10(b).
**Критерий приёмки.** Файл открывается, три листа на месте, число строк реестра равно числу записей выборки, шапка заморожена, даты в ISO 8601, колонка `id` скрыта.
**Приоритет.** Must

### URS-050 — Выгрузка PDF
**Требование.** Система должна формировать на сервере PDF с титульной страницей (заголовок, период, фильтры, актор, время, версия приложения, идентификатор отчёта), таблицей с повтором шапки, нумерацией «страница X из Y», колонтитулом с идентификатором и временем на каждой странице, встроенным шрифтом с кириллицей.
**Источник.** Раздел 9c / A-1.2 / Part 11 §11.10(b).
**Критерий приёмки.** Файл открывается, кириллица читаема без системных шрифтов, на каждой странице есть идентификатор отчёта и время, титул содержит актора и SHA версии.
**Приоритет.** Must

### URS-051 — Выгрузка — контролируемое действие
**Требование.** Каждая выгрузка должна писать событие `export` с форматом, фильтрами, числом записей, актором и `request_id`.
**Источник.** Раздел 3, пункт 6 / раздел 9c / критерий готовности 7.
**Критерий приёмки.** После GET export в журнале есть `export`, поля совпадают с фактическим файлом; повторная выгрузка даёт новое событие.
**Приоритет.** Must

### URS-052 — Имя файла выгрузки
**Требование.** Имя файла должно иметь вид `cs-registry_<YYYY-MM-DD>_<HHMM>_<short-request-id>.<ext>`.
**Источник.** Раздел 9c.
**Критерий приёмки.** Заголовок `Content-Disposition` содержит имя, удовлетворяющее шаблону, с датой UTC формирования и расширением `xlsx` или `pdf`.
**Приоритет.** Must

### URS-053 — Выгрузка не расширяет персональные данные
**Требование.** Экспорт должен включать только поля реестра, необходимые по делу, и не добавлять email, хеши паролей и прочие поля `users` сверх отображаемых ФИО владельца процесса, владельца системы и владельца качества.
**Источник.** Раздел 9c / контекстная диаграмма.
**Критерий приёмки.** В XLSX и PDF нет колонок `password_hash`, `mfa_secret`, `email`; ФИО владельца процесса и владельца системы присутствуют; ФИО владельца качества — если поле задано.
**Приоритет.** Must

### URS-054 — Право выгрузки у всех ролей просмотра
**Требование.** Выгрузка XLSX и PDF должна быть доступна ролям `admin`, `editor`, `viewer` и `auditor`.
**Источник.** Раздел 6, строка «Экспорт» / A-1.2 (XLSX и PDF вместо CSV).
**Критерий приёмки.** GET export с `format=xlsx` и `format=pdf` для каждой из четырёх ролей возвращает 200 и файл.
**Приоритет.** Must

### URS-055 — Потоковое формирование
**Требование.** Файл должен собираться на сервере потоково, без загрузки всего набора во память клиента до начала передачи.
**Источник.** Раздел 9c, общее.
**Критерий приёмки.** Ответ начинается с файлового content-type и тела файла; клиентский JS не строит книгу из полного JSON всего реестра.
**Приоритет.** Must

## Аутентификация и сессии

### URS-056 — Персональные учётные записи
**Требование.** Система должна аутентифицировать административных пользователей по персональным учёткам: вход и выход.
**Источник.** Раздел 3, пункт 5 / раздел 10.
**Критерий приёмки.** Верные учётные данные выдают сессию и пишут `login`; выход уничтожает сессию и пишет `logout`; без сессии защищённые маршруты недоступны.
**Приоритет.** Must

### URS-057 — Политика пароля
**Требование.** Пароли должны храниться как Argon2id и приниматься длиной не менее 12 символов.
**Источник.** Раздел 9 / Auth.js + Argon2id.
**Критерий приёмки.** Пароль 11 символов при создании пользователя отклоняется; в БД колонка `password_hash` не равна открытому паролю и соответствует Argon2id.
**Приоритет.** Must

### URS-058 — Блокировка после неудач
**Требование.** Система должна блокировать вход после 5 неудачных попыток за 15 минут.
**Источник.** Раздел 9 / Part 11 §11.10(g).
**Критерий приёмки.** Шестая попытка в окне 15 минут с верным паролем не создаёт сессию; в аудите есть серия `login_failed`.
**Приоритет.** Must

### URS-059 — Параметры сессии
**Требование.** Сессия должна храниться в httpOnly cookie с `SameSite=Lax`.
**Источник.** Раздел 4, Auth.js.
**Критерий приёмки.** В ответе login cookie имеет флаги HttpOnly и SameSite=Lax; документ JS `document.cookie` не содержит идентификатора сессии.
**Приоритет.** Must

### URS-060 — Ротация сессии при смене пароля
**Требование.** Смена пароля должна инвалидировать предыдущие сессии пользователя и выдать новую текущему, если смена выполняется им самим.
**Источник.** Раздел 4 / Part 11 §11.10(h).
**Критерий приёмки.** После смены пароля прежний cookie не проходит аутентификацию.
**Приоритет.** Must

### URS-061 — Отзыв сессий при деактивации
**Требование.** Деактивация пользователя должна отзывать все его сессии немедленно.
**Источник.** Раздел 9a / Part 11 §11.10(h) / раздел 4.
**Критерий приёмки.** После `is_active = false` следующий запрос с прежним cookie возвращает 401.
**Приоритет.** Must

### URS-062 — Истечение сессии
**Требование.** Сессия должна иметь конечный срок жизни в зависимости от роли: 30 минут для `admin`, 10 минут для `editor`, `viewer` и `auditor`. По истечении пользователь проходит вход заново. Значения задаются `SESSION_MINUTES_ADMIN` и `SESSION_MINUTES_DEFAULT`.
**Источник.** Part 11 §11.10(h). Решение заказчика 29.10.2026.
**Критерий приёмки.** Cookie успешного login для `admin` имеет `Max-Age=1800`, для `viewer` — `Max-Age=600`; запрос с просроченным cookie возвращает 401 и не выполняет мутацию.
**Приоритет.** Must

### URS-063 — Rate limit на вход
**Требование.** Система должна ограничивать частоту запросов на вход на уровне Caddy.
**Источник.** Раздел 9 / раздел 4 Caddy rate limit.
**Критерий приёмки.** Серия запросов login сверх лимита получает 429 до проверки пароля в приложении либо на edge.
**Приоритет.** Must

### URS-064 — Rate limit на поиск
**Требование.** Система должна ограничивать частоту поисковых запросов.
**Источник.** Раздел 9.
**Критерий приёмки.** Превышение лимита `GET /api/v1/systems` с `q` возвращает 429.
**Приоритет.** Should

### URS-065 — Восстановление доступа
**Требование.** Восстановление пароля через SMTP в MVP не входит; пароль сбрасывает администратор вручную.
**Источник.** Решение заказчика 29.10.2026.
**Критерий приёмки.** В API нет маршрута восстановления по SMTP; администратор сбрасывает пароль через изменение учётки (`password_reset`).
**Приоритет.** Could

## Целостность данных GxP

### URS-066 — Пользователи не удаляются физически
**Требование.** Система должна деактивировать пользователей (`is_active = false`) и не должна физически удалять строки `users`.
**Источник.** Раздел 5 `users` / ALCOA+ Attributable.
**Критерий приёмки.** В API нет DELETE `/users/:id`; деактивация сохраняет строку и FK со стороны `systems`.
**Приоритет.** Must

### URS-067 — Транзакционность данных и аудита
**Требование.** Запись изменения реестра и события аудита должна выполняться атомарно.
**Источник.** Раздел 4 (аудит обязан быть транзакционным) / раздел 7 Accurate.
**Критерий приёмки.** Искусственный сбой после UPDATE `systems` до INSERT аудита откатывает оба шага; в БД нет изменения без события и события без изменения для успешных мутаций.
**Приоритет.** Must

### URS-068 — Русский язык интерфейса
**Требование.** Интерфейс и хранимые текстовые данные должны поддерживать русский язык.
**Источник.** Допущение A-3.
**Критерий приёмки.** Карточка с кириллическим `name` сохраняется и отображается без искажения кодировки; подписи экранов на русском.
**Приоритет.** Must

### URS-069 — Один тенант
**Требование.** В MVP система обслуживает одну организацию; схема не должна исключать появление тенанта позже.
**Источник.** Допущение A-2.
**Критерий приёмки.** Нет экранного переключателя организаций; в модели нет жёстких уникальных индексов, которые запретили бы добавить `tenant_id` отдельной миграцией без ломания смысла `code`.
**Приоритет.** Must

### URS-070 — Резервное копирование
**Требование.** Система должна ежедневно создавать шифрованный дамп вне VPS с ротацией 7 дневных, 4 недельных, 6 месячных копий.
**Источник.** Раздел 9 / критерий готовности 5. Обоснование: 21 CFR Part 11 §11.10(c) требует защиты записей на протяжении всего срока хранения; ALCOA+ (Enduring, Available) — чтобы записи оставались читаемыми и доступными. CFR буквально не предписывает резервное копирование как процедуру: требование выводится из защиты и доступности записей, а не из буквы пункта 11.10(c).
**Критерий приёмки.** В хранилище бэкапов присутствуют объекты в заданной ротации; дамп не читается без ключа шифрования. Срок хранения сверх ротации 7/4/6 не зафиксирован (открытый вопрос, решение отложено 29.10.2026).
**Приоритет.** Must

### URS-071 — Проверка восстановления
**Требование.** Восстановление из резервной копии должно быть выполнено и подтверждено не реже одного раза в месяц, для MVP — хотя бы один раз вручную до демонстрации.
**Источник.** Раздел 9 / критерий готовности 5. Обоснование то же, что у URS-070: §11.10(c) и ALCOA+ Enduring/Available. Проверка восстановления показывает, что защита записей не сводится к наличию файла дампа. CFR буквально не предписывает бэкапы и регламент восстановления как процедуру — требование выводится из защиты и доступности записей, а не из буквы пункта 11.10(c).
**Критерий приёмки.** Протокол восстановления фиксирует успешный подъём БД из дампа и совпадение контрольной выборки `systems` и последнего `audit_events.hash`.
**Приоритет.** Must

### URS-072 — TLS и заголовки безопасности
**Требование.** Внешний доступ должен идти только по TLS; Caddy выставляет security headers. HSTS — после проверки домена.
**Источник.** Раздел 9 / A-4.
**Критерий приёмки.** HTTP-запрос к внешнему порту перенаправляется на HTTPS; в ответе Caddy присутствуют согласованные security headers.
**Приоритет.** Must

### URS-073 — Логи без секретов и лишних ПДн
**Требование.** Структурированные логи с correlation ID не должны содержать пароли, токены и персональные данные сверх необходимого.

## Ограничения Part 11

### URS-076 — Применение Part 11 к разработке
**Требование.** К разработке применяется 21 CFR Part 11. ЭП не требуется (решение заказчика 29.10.2026). Ограничение области фиксируется в валидационном отчёте.
**Источник.** A-1 / раздел 9a. Решение заказчика 29.10.2026.
**Критерий приёмки.** В валидационном комплекте есть явная фраза «ЭП не требуется (решение заказчика 29.10.2026)»; функции 11.10(b)–(e), (g), (h) закрыты требованиями этого URS.
**Приоритет.** Must

### URS-077 — ЭП не требуется
**Требование.** ЭП не требуется (решение заказчика 29.10.2026). Критичные действия принимаются с непустым `reason` и снимком актора.
**Источник.** Решение заказчика 29.10.2026 / раздел 9a.
**Критерий приёмки.** Критичные действия принимаются с непустым `reason`; в схеме события есть `reason`, `actor_id`, `actor_username`, `actor_role`; в URS, FS и README есть фраза «ЭП не требуется (решение заказчика 29.10.2026)».
**Приоритет.** Must

### URS-078 — Точные и полные копии
**Требование.** Система должна давать точные и полные копии данных реестра в читаемом виде средствами XLSX и PDF.
**Источник.** Part 11 §11.10(b) / раздел 9c.
**Критерий приёмки.** Выгрузка с теми же фильтрами, что и экран, содержит те же `code` и значения отображаемых полей; лист параметров позволяет воспроизвести выборку.
**Приоритет.** Must

### URS-079 — Защита записей от изменения и удаления
**Требование.** Записи аудита должны быть защищены от изменения и удаления в течение срока хранения.
**Источник.** Part 11 §11.10(c) / раздел 7.
**Критерий приёмки.** Совокупность URS-041, URS-042, URS-043 выполняется; прикладной API не содержит методов правки журнала.
**Приоритет.** Must

### URS-080 — Ограничение доступа по полномочиям
**Требование.** Доступ к функциям должен ограничиваться ролью, проверяемой на сервере.
**Источник.** Part 11 §11.10(d) / раздел 6.
**Критерий приёмки.** Матрица FS для всех эндпоинтов раздела 10 совпадает с фактическими кодами 200/401/403.
**Приоритет.** Must

### URS-081 — Аудит-трейл по 11.10(e)
**Требование.** Аудит-трейл должен содержать дату, время UTC, пользователя, тип действия, значения до и после, причину для критичных действий и request ID.
**Источник.** Part 11 §11.10(e) и (e)(1)–(e)(5).
**Критерий приёмки.** Каждое событие изменения имеет `occurred_at`, снимок актора, `action`, и при изменении полей — `before`/`after`; критичные — ещё и `reason`.
**Приоритет.** Must

### URS-082 — Последовательность этапов
**Требование.** Обязательный workflow согласования в MVP отсутствует; единственная последовательность — смену статуса валидации выполняет только `admin` с причиной.
**Источник.** Part 11 §11.10(f) / раздел 9a, «не применимо».
**Критерий приёмки.** Нет экранного маршрута согласования; смена `validation_status` недоступна не-admin; обоснование ограничения задокументировано здесь и в контексте.
**Приоритет.** Must

### URS-083 — Проверка учётных данных
**Требование.** Система должна проверять полномочия и валидность учётных данных: сессия, Argon2id, блокировка, деактивация.
**Источник.** Part 11 §11.10(g).
**Критерий приёмки.** Деактивированный пользователь не входит; неверный пароль не выдаёт сессию; истёкшая сессия не проходит.

### URS-084 — Актуальность сессии и учётки
**Требование.** Система должна завершать сессию по истечении срока и при деактивации пользователя.

**Требование.** Единственный источник ввода данных — аутентифицированный пользователь через интерфейс; отдельная проверка устройства не применяется.

### URS-112 — Фильтры списка 0.9.0
**Требование.** Список фильтруется по домену, компании, GxP-критичности, GAMP и владельцу.
**Источник.** Задание 0.9.0, п. 6.
**Критерий приёмки.** API принимает параметры и отклоняет неизвестные значения. Открыто: UI-фильтр по владельцу и фильтр по любому полю (см. CHANGELOG 0.9.0).
**Приоритет.** Must

### URS-113 — Безопасные ссылки документации
**Требование.** Внутренняя документация и документация подрядчика — список (название + ссылка); разрешены только http(s) и `\\сервер\ресурс`; изменения ссылок аудируются.
**Источник.** Задание 0.9.0, п. 7.
**Критерий приёмки.** `javascript:` и `data:` — 400 с русским сообщением; CHECK в БД; `changed_fields` содержит `internal_documents`.
**Приоритет.** Must

### URS-114 — Ошибки формы под полями и лог отказа
**Требование.** Любая ошибка проверки формы показывается русским сообщением под соответствующим полем; ответ содержит `requestId`; лог отказа содержит requestId, маршрут и имена полей без значений.
**Источник.** Задание 0.9.0, п. 8.
**Критерий приёмки.** `tests/integration/user-validation.test.ts`: email `loli@com` → `fields[email]`, в логе нет значения и пароля.
**Приоритет.** Must

### URS-115 — Транзакционные миграции
**Требование.** Каждая миграция применяется одной транзакцией; при ошибке база остаётся в прежнем состоянии.
**Источник.** Ревью 0.9.0.
**Критерий приёмки.** `scripts/apply-migrations.ts` выполняет файл и запись хеша в `sql.begin`.
**Приоритет.** Must

### URS-116 — Production-поставка в контейнерах
**Требование.** Приложение поставляется Docker-образом без root, с healthcheck; БД не публикуется наружу; миграции — отдельный одноразовый шаг.
**Источник.** Ревью 0.9.0, DEPLOY-PROD.md.
**Критерий приёмки.** `docker compose -f docker-compose.prod.yml up` на пустой базе: миграции 0000–0006, `/api/health` = ok, процесс uid 1000.
**Приоритет.** Must

# Комплект шаблонов валидации компьютеризированных систем (CSV)

Шаблоны в формате Markdown на русском языке для документов жизненного цикла валидации компьютеризированной системы: от плана валидации (VP) до отчёта о валидации (VR), включая протокол PQ / UAT. Ориентированы на Правила GMP ЕАЭС (Решение Совета ЕЭК №77, Приложения 11 и 15), EU GMP Annex 11/15 и PIC/S как эталон, а также методологию GAMP 5 (2-е изд.). Рынок — ЕАЭС.

Шаблоны универсальные: данных конкретной компании в них нет.

## 1. Состав комплекта

| № | Файл | Документ | Когда разрабатывается |
|---|---|---|---|
| 01 | `01-VP.md` | План валидации (Validation Plan) | Первым, после решения о внедрении системы |
| 02 | `02-URS.md` | Спецификация требований пользователя | До выбора или настройки системы |
| 03 | `03-FS.md` | Функциональная спецификация | После URS; часто от поставщика |
| 04 | `04-Risk-Assessment.md` | Оценка рисков по функциям FS (на уровне системы + функциональная, FMEA / GAMP M3) | После утверждения URS и FS |
| 05 | `05-DIA.md` | Оценка целостности данных (поток данных, ALCOA+, audit trail, ЭЗ/ЭП) | После FS и RA, до протоколов |
| 06 | `06-IQ.md` | Протокол квалификации монтажа + тест-скрипты | Утверждается до установки или исполнения |
| 07 | `07-OQ.md` | Протокол квалификации функционирования + тест-скрипты | Утверждается до исполнения, исполняется после IQ |
| 08 | `08-PQ.md` | Протокол квалификации эксплуатации / приёмочных испытаний пользователей (PQ / UAT — единый этап) | Утверждается до исполнения; исполняется после IQ и OQ, до закрытия RTM и VR |
| 09 | `09-RTM.md` | Матрица прослеживаемости + журнал отклонений | Ведётся с момента URS, закрывается перед VR |
| 10 | `10-VR.md` | Отчёт о валидации с решением о выпуске | Последним |
| — | `BACKLOG.md` | Шаблоны, которые ещё не разработаны | — |
| — | `AUDIT-2026-11-27.md` | Отчёт об аудите актуальности комплекта (27.11.2026) | — |

Не входят в комплект: оценка поставщика (проводится по отдельной процедуре оценки поставщиков <заполнить: № СОП>; требования к поставщику и соглашению остаются в URS, DIA и VP со ссылкой на неё) и DS / CS (спецификация дизайна и конфигурации). Конфигурацию системы всё равно нужно документировать: перечень параметров и матрица прав ведутся в 03-FS, раздел 6.9, и проверяются в IQ-006 (Рек. ЕЭК №25 п.105(а), п.170). PQ / UAT — обязательный этап (`08-PQ.md`); исключение допускается только с обоснованием в VP (раздел 8.2). Остальные шаблоны — в `BACKLOG.md`.

## 2. Порядок жизненного цикла

```
VP ─► URS ─► FS ─► RA (по функциям FS) ─► DIA
                                           │
VR ◄── RTM (закрытие) ◄── PQ ◄── OQ ◄── IQ ◄── протоколы IQ/OQ/PQ утверждены
```

Порядок документов: VP, URS, FS, RA, DIA, IQ, OQ, PQ, RTM, VR. Оценка поставщика вне комплекта (отдельная процедура компании).

V-модель (связь спецификаций и проверок):

```
URS ──────────────────────── PQ / UAT
   FS ──────────────────── OQ
      [конфигурация: 03-FS, разд. 6.9] ── IQ
```

## 3. Как документы связаны

- **VP** определяет перечень документов (раздел 8.2), глубину тестирования по приоритету риска (10.2), классы отклонений (12.1), переходы между этапами (13) и условия выпуска (15).
- **URS** даёт ID требований `URS-xxx` и флаг GxP. Это вход для FS, RA, DIA и RTM.
- **FS** раскрывает `URS-xxx` в функции `FS-xxx`. Таблица соответствия URS→FS переносится в RTM.
- **RA** выполняется после FS и опирается на функции FS (FS-xx → RA-xx), а не только на требования URS. Она присваивает каждой GxP-функции приоритет риска, который определяет глубину OQ (по таблице VP 10.2).
- **DIA** даёт меры по целостности данных `DIA-xxx`, которые проверяются в IQ/OQ или закрываются СОПами.
- **IQ/OQ/PQ** содержат тесты `IQ-xxx`, `OQ-xxx`, `PQ-xxx`. Тесты IQ/OQ ссылаются на `URS-xxx` / `FS-xxx`; сквозные сценарии PQ — на `URS-xxx`, подтверждаемые на уровне процесса.
- **RTM** связывает всё в одну строку (URS → FS → RA → IQ / OQ / PQ) и ведёт журнал `DEV-xxx` с обязательным номером записи в EQMS.
- **VR** опирается на RTM, журнал отклонений и итоги протоколов IQ/OQ/PQ. Все отклонения закрываются в EQMS до утверждения VR.

## 4. Соглашения об идентификаторах

| Объект | Формат | Пример | Правило |
|---|---|---|---|
| Документ | `CSV-<КОД СИСТЕМЫ>-<ТИП>-<NNN>` | CSV-LIMS-VP-001 | Тип: VP, URS, FS, RA, DIA, IQ, OQ, PQ, RTM, VR. Можно заменить на схему из СОП компании |
| Требование пользователя | `URS-xxx` | URS-003 | Сквозная нумерация; номера не переиспользуются; удалённые помечаются «Удалено» |
| Функция FS | `FS-xxx` | FS-003 | По возможности тот же номер, что у основного URS (URS-003 → FS-003). Для дополнительных функций — свободные номера |
| Риск | `RA-xxx` | RA-003 | Номер совпадает с номером функции FS (FS-003 → RA-003), если риск оценивается по одной функции. Оценка на уровне системы — `RA-I01…` |
| Целостность данных | `DIA-xxx`; чек-лист ЭЗ/ЭП: `ER-xx`, `ES-xx` | DIA-020 | — |
| Параметр конфигурации | `CFG-xx` | CFG-02 | Ведётся в 03-FS, раздел 6.9; проверяется в IQ-006 |
| Тест IQ / OQ / PQ | `IQ-xxx`, `OQ-xxx`, `PQ-xxx` | OQ-003 | Нумерация в пределах протокола |
| Шаг теста | `<Тест-ID>.<NN>` | OQ-003.02 | — |
| Нескриптовый тест | `OQ-Xnn` | OQ-X01 | — |
| Доказательство | `<Тест-ID>-E<NN>` | OQ-003-E01 | Скриншот, выгрузка или лог |
| Отклонение | `DEV-xxx` | DEV-002 | Единый реестр в 09-RTM. Каждое отклонение обязательно регистрируется в EQMS компании |
| Запись в EQMS | номер по системе компании | EQMS-DEV-2026-0152 (ПРИМЕР) | Обязательное поле «№ записи в EQMS / ссылка» в таблицах отклонений IQ, OQ, PQ, RTM, VR |
| Запрос на изменение | `CR-xxx` (или по СОП) | CR-015 | — |

Сквозной пример в шаблонах (строки **ПРИМЕР**): URS-001…009, 020, 030 → FS-001…009 (конфигурация CFG-01…03) → RA-тех же номеров → IQ-002, 004, 005, 006, 007 / OQ-001…009 → PQ-001…003 (сквозные сценарии) → DEV-001, 002 (записи в EQMS). Проследить цепочку можно по 09-RTM, раздел 6.

## 5. Как заполнять

1. Скопируйте шаблон, переименуйте файл по ID документа.
2. Заполните титульный лист и лист согласования. Роли подписантов сверьте с СОП компании.
3. Заполните все поля `<заполнить: ...>`. Неприменимое помечайте «Н/П» с обоснованием, а не удаляйте молча.
4. Прочитайте блоки `> Подсказка:`: в них указано, что писать и насколько подробно для категорий GAMP 3/4/5. Удалите подсказки перед утверждением.
5. Строки **ПРИМЕР** замените своими или удалите. Примеры показывают формат, а не обязательное содержание.
6. Ссылки на нормативы оставляйте с теми номерами пунктов, которые указаны в шаблоне: они сверены с официальными текстами. Добавляя новую ссылку, указывайте номер пункта, только если сверили его с первоисточником, иначе — название раздела.
7. Протоколы IQ/OQ/PQ утверждаются **до** исполнения. Фактические результаты вносит исполнитель в момент выполнения, по правилам GDP (раздел 8 протоколов).
8. Перед VR закройте RTM: 0 GxP-требований без покрытия, 0 тестов без трассировки.

## 6. Масштабирование по категориям GAMP 5

| Документ | Кат. 3 | Кат. 4 | Кат. 5 |
|---|---|---|---|
| VP | Краткий | Полный | Полный |
| URS | Ключевые требования intended use | + настройки, роли, workflow, DI | Полный набор для FS и дизайна |
| RA | На уровне системы + короткая функциональная | Функциональная по настроенным GxP-функциям | Функциональная по всем кастомным GxP-функциям |
| FS | Документация поставщика | FS поставщика + ревью / дополнение | Полная FS |
| DIA | Короткая | Полная | Полная |
| IQ | Версии, документация | + базовая конфигурация | + сборка из репозитория |
| OQ | Минимальная / объединена с PQ | Настроенные GxP-функции | Полное покрытие кастомных функций |
| PQ / UAT | 1–3 сквозных сценария intended use; может объединяться с OQ | Сквозные сценарии основных GxP-процессов, роли, восстановление | + кастомные функции, интерфейсы, рабочий диапазон |
| RTM | URS → тест (IQ / OQ-PQ) | URS → FS → RA → IQ / OQ → PQ | URS → FS → RA → IQ / OQ → PQ |

Таблица — отраслевая практика по GAMP 5 (вторичные источники). Категория — один из факторов; глубину определяют GxP-влияние, сложность, новизна и оценка рисков.

## 7. Статус нормативной базы (проверено 27.11.2026)

Сверено по текстам решений (docs.eaeunion.org, alta.ru).

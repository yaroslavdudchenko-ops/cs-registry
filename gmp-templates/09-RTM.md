## 4. Термины и сокращения

| Термин | Определение |
|---|---|
| Прямая трассировка | Требование → тест (каждое требование покрыто) |
| Обратная трассировка | Тест → требование (каждый тест обоснован требованием) |
| DEV-ID | Идентификатор отклонения в проекте, формат `DEV-xxx` |
| EQMS | Электронная система управления качеством компании; каждое отклонение обязательно регистрируется в ней, номер записи указывается в журнале |

## 5. Правила ведения

> Подсказка:
> - Одна строка — одно требование URS. Если требование покрыто несколькими FS или тестами, перечислите их через запятую.
> - Колонка «Покрытие» заполняется, если требование не тестируется: «Поставщик (ID документа; оценка поставщика — по отдельной процедуре оценки поставщиков <заполнить: № СОП>)», «Процедура (ID СОП)», «Не GxP — не тестируется (RA-xxx)».
> - После исполнения протоколов заполните колонки «Результат» и «DEV-ID».
> - Проверка при ревью: нет GxP-требований без покрытия; нет тестов без требования; статусы совпадают с исполненными протоколами.
> - **Кат. 3**: RTM может быть короткой (URS → IQ / OQ-PQ). **Кат. 4/5**: полная цепочка URS → FS → RA → IQ / OQ → PQ.
> - Для больших систем RTM удобнее вести в таблице (xlsx) или в ALM-инструменте. Этот шаблон задаёт состав колонок.
